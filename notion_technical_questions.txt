기술 질문
호스트란?
호스트는 네트워크에서 접속 대상이 되는 서버나 장치를 가리키는 이름입니다. URL에서는 `https://api.example.com:443/users`에서 `api.example.com` 부분이 호스트입니다.
호스트는 도메인 이름일 수도 있고 IP 주소일 수도 있습니다. 예를 들어 `example.com`, `api.example.com`, `127.0.0.1`은 모두 URL의 호스트가 될 수 있습니다.
호스트와 도메인은 겹치는 경우가 많지만 완전히 같은 말은 아닙니다. 도메인은 사람이 읽기 쉬운 이름 체계이고, 호스트는 실제 요청을 보낼 접속 대상입니다. 예를 들어 `api.example.com`은 도메인 이름이면서 동시에 URL 안에서는 호스트이고, `127.0.0.1`은 호스트가 될 수 있지만 일반적인 도메인 이름은 아닙니다.
Origin이란?
Origin은 브라우저가 보안 정책에서 출처를 판단할 때 사용하는 기준으로, scheme, host, port의 조합입니다. 예를 들어 `https://api.example.com:443`에서 scheme은 `https`, host는 `api.example.com`, port는 `443`입니다.
두 URL의 scheme, host, port가 모두 같으면 같은 Origin이고, 하나라도 다르면 다른 Origin입니다. `https://example.com`과 `http://example.com`은 scheme이 달라 다른 Origin이고, `https://app.example.com`과 `https://api.example.com`은 host가 달라 다른 Origin입니다.
CORS와 Same-Origin Policy는 이 Origin을 기준으로 동작합니다. 그래서 서브 도메인이 같아 보이거나 같은 회사의 도메인처럼 보여도, 브라우저 입장에서는 Origin이 다르면 다른 Origin으로 판단할 수 있습니다.
도메인이란?
도메인은 사람이 읽기 쉬운 인터넷 주소 이름입니다. 예를 들어 `example.com`은 도메인이고, `api.example.com`이나 `admin.example.com`은 `example.com` 아래의 서브 도메인으로 볼 수 있습니다.
부모 도메인이라는 표현은 보통 `example.com`이 `api.example.com`의 상위에 있다는 의미로 느슨하게 사용합니다.
쿠키의 Domain 속성을 설정하면 특정 도메인과 그 하위 도메인에 쿠키를 보낼 수 있습니다. 예를 들어 `Domain=example.com`으로 설정한 쿠키는 조건을 만족하면 `app.example.com`이나 `api.example.com`에도 전송될 수 있습니다. 반대로 Domain을 지정하지 않은 host-only 쿠키는 기본적으로 쿠키를 설정한 호스트에만 전송됩니다.
CSRF란?
CSRF는 쿠키가 요청에 자동으로 담기는 것을 이용해, 사용자가 의도하지 않은 요청을 강제로 실행시키는 공격입니다.
방어 방법으로는 첫째, 서버에서 예측 불가능한 CSRF 토큰을 생성해서 세션에 저장하고 클라이언트에 전달합니다. 이후, 클라이언트는 폼이나 요청 헤더에 이 토큰을 포함시켜 서버에서 검증합니다. 둘째,  SameSite를 Strict나 Lax로 설정하면 외부 사이트에서 쿠키가 자동으로 전송되지 않습니다.
SameSite란?
SameSite는 쿠키가 다른 사이트 요청에도 함께 전송될 수 있는지를 제한하는 보안 속성입니다.
여기서 같은 사이트라는 기준은 전체 URL이 아니라 보통 scheme과 등록 도메인입니다. 예를 들어 `https://app.example.com`과 `https://api.example.com`은 host가 달라 다른 Origin이지만, 둘 다 `https + example.com` 기준으로 묶이기 때문에 같은 site로 볼 수 있습니다.
브라우저는 SameSite 설정에 따라 크로스 사이트 요청에서 쿠키를 자동으로 보내줄지 말지를 결정하며, 이를 통해 CSRF 공격을 방지하는 것이 목적입니다.
Strict은 같은 사이트 요청에서만 쿠키를 전송하며, 외부 사이트에서 들어온 요청에는 쿠키를 보내지 않습니다.
Lax는 기본값으로, 대부분의 크로스 사이트 요청에서는 쿠키를 보내지 않지만, 링크 클릭과 같은 일부 안전한 GET 요청에는 쿠키를 허용합니다.
None는 모든 크로스 사이트 요청에 쿠키를 전송하며, 이 경우 반드시 Secure 속성과 함께 사용해야 합니다. Secure 없이 SameSite=None만 설정하면 현대 브라우저에서는 해당 쿠키가 저장되지 않거나 무시될 수 있습니다.
Secure란?
쿠키에 적용하는 보안 속성으로, 해당 쿠키가 HTTPS 연결에서만 전송되도록 제한하는 옵션입니다.
이를 통해 네트워크 구간에서 평문 HTTP 통신 중 쿠키가 탈취되는 것을 방지할 수 있으며, 인증 정보와 같은 민감한 쿠키를 안전하게 보호하기 위해 HttpOnly, SameSite 옵션과 함께 사용되는 것이 일반적입니다.
HttpOnly란?
HttpOnly는 쿠키에 적용하는 보안 옵션으로, 자바스크립트에서 해당 쿠키에 접근하지 못하도록 제한하는 속성입니다.
이를 통해 XSS 공격으로 쿠키가 탈취되는 것을 방지할 수 있으며, 쿠키는 브라우저가 HTTP 요청에만 자동으로 포함시켜 서버와 통신하는 용도로만 사용됩니다. 따라서 인증 정보나 세션 쿠키처럼 민감한 데이터 보호를 위해 주로 사용됩니다.
XSS란?
XSS는 스크립트를 웹 페이지에 삽입해서 실행시키는 공격입니다.
방어 방법으로는 사용자의 입력값을 그대로 실행하지 않도록 출력 위치에 맞게 이스케이프 처리하는 것이 중요합니다. HTML 입력을 허용해야 한다면 검증된 라이브러리로 sanitize하고, dangerouslySetInnerHTML이나 innerHTML 같은 API는 가급적 사용하지 않아야 합니다. 
이스케이프 처리란?
이스케이프 처리는 특수 문자를 무해한 문자열로 변환하는 것입니다. 예를 들어 사용자가 <script>alert('해킹')</script> 같은 코드를 입력하면 그대로 실행될 수 있습니다. 이스케이프 처리를 하면 이런 특수 문자들을 HTML 엔티티로 변환합니다.
React 같은 프레임워크는 자동으로 이스케이프 처리를 해줍니다. 그래서 {userName}처럼 변수를 렌더링하면 안전하게 처리됩니다. 하지만 dangerouslySetInnerHTML을 사용하면 이스케이프를 건너뛰기 때문에 위험할 수 있습니다.
HTML 엔티티란?
HTML 엔티티는 <, >, &처럼 HTML 문법으로 해석될 수 있는 문자를 안전하게 표현하기 위해 &lt;, &gt; 같은 형태로 치환하는 표기법이며, 렌더링 오류 방지와 XSS 공격 예방에 사용됩니다.
JSX란?
JSX는 JavaScript 안에서 HTML과 유사한 형태로 UI 구조를 작성할 수 있게 해주는 문법 확장입니다. 별도의 프로그래밍 언어는 아닙니다.
JSX를 사용하면 UI 관련 코드를 직관적이고 가독성 높게 작성할 수 있어, 재사용 가능한 컴포넌트를 쉽게 만들 수 있습니다.
브라우저는 JSX를 직접 해석할 수 없기 때문에 Babel이나 SWC 같은 트랜스파일러를 통해 일반 JavaScript 코드로 변환됩니다. React가 JSX를 직접 변환하는 것이 아니라, Vite나 Next.js 같은 빌드 도구가 내부적으로 Babel 또는 SWC를 사용해 변환합니다.
JSX의 중요한 보안 특징은 기본적으로 모든 값을 이스케이프 처리한다는 점입니다. 문자열로 입력된 내용은 자동으로 안전하게 변환되어 XSS(Cross-Site Scripting) 공격을 방지합니다.
트랜스파일러란?
트랜스파일러는 한 프로그래밍 언어로 작성된 소스 코드를 동일한 수준의 다른 언어 코드로 변환하는 도구로, 주로 실행 환경의 호환성을 확보하거나 최신 문법을 지원하지 않는 환경에서도 코드를 실행할 수 있도록 변환하는 역할을 합니다.
대표적으로 Babel이나 TypeScript 컴파일러가 최신 JavaScript 또는 TypeScript 코드를 구형 JavaScript로 변환하는 데 사용됩니다.
컴파일러는 소스 코드를 다른 형태의 실행 가능한 코드로 변환하는 넓은 개념입니다. 트랜스파일러는 그중에서도 비슷한 수준의 언어 사이에서 코드를 변환하는 도구를 말합니다. 예를 들어 Babel은 최신 JavaScript를 구형 JavaScript로 변환합니다.
컴파일러란?
컴파일러는 사람이 작성한 고급 언어 코드를 어휘·구문·의미 분석 과정을 거쳐 실행 전에 컴퓨터가 이해할 수 있는 코드로 변환하며, 이 과정에서 문법 오류를 사전에 검출하고 코드 최적화를 수행하는 프로그램입니다.
폴리필이란?
최신 JavaScript 기능을 지원하지 않는 구버전 브라우저에서도 동일한 기능을 사용할 수 있도록, 해당 기능을 JavaScript 코드로 직접 구현해 추가하는 방식을 말합니다.
예를 들어 IE11은 Promise나 Array.prototype.includes 같은 최신 API를 지원하지 않는데, 폴리필은 이러한 API를 JavaScript로 구현해 전역 객체에 추가함으로써 기존 코드가 동일하게 동작하도록 만듭니다.
트랜스파일과의 차이점은, 트랜스파일은 빌드 단계에 문법을 변환하는 작업인 반면, 폴리필은 실행 시점에 존재하지 않는 기능을 런타임에 추가한다는 점입니다.
단점으로는 필요한 폴리필이 많아질수록 번들 크기가 증가해 초기 로딩 성능에 영향을 줄 수 있다는 점이 있습니다.
프로세스란?
프로세스는 실행 중인 프로그램을 의미하며, 운영체제로부터 자원을 할당받는 단위입니다.
스레드란?
스레드는 프로세스 내에서 실제로 일을 처리하는 실행 흐름입니다.
하나의 프로세스는 최소 하나 이상의 스레드를 가지며, 프로세스가 실행되면 기본적으로 메인 스레드가 생성됩니다. 프로세스를 하나의 공장이라고 비유하면, 스레드는 그 안에서 일하는 작업자들이라고 할 수 있습니다.
멀티 스레드 / 싱글 스레드란?
싱글 스레드와 멀티 스레드는 작업을 처리하는 실행 흐름의 개수에 따른 프로그램 실행 모델입니다.
싱글 스레드는 하나의 실행 흐름만으로 작업을 순차적으로 처리하는 방식으로, 구조가 단순하고 상태 관리가 쉬운 대신 하나의 작업이 오래 걸리면 전체 실행이 지연될 수 있습니다.
반면 멀티 스레드는 여러 실행 흐름을 동시에 사용해 작업을 병렬로 처리하는 방식으로, 처리 성능을 높일 수 있지만 동기화와 경쟁 상태 관리가 복잡해질 수 있습니다.
자바스크립트가 싱글 스레드로 동작하는 이유는?
자바스크립트가 싱글 스레드로 동작한다는 것은 JavaScript 코드 실행이 기본적으로 하나의 콜 스택에서 순차적으로 처리된다는 뜻입니다.
이렇게 설계된 가장 큰 이유는 DOM 조작과 실행 순서를 단순하고 예측 가능하게 만들기 위해서입니다. 여러 스레드가 동시에 같은 DOM을 수정할 수 있다면, 한쪽은 요소를 삭제하고 다른 쪽은 같은 요소의 텍스트를 바꾸는 식의 충돌이 생길 수 있습니다. 이를 막으려면 락이나 동기화 같은 복잡한 처리가 필요합니다.
대신 브라우저는 네트워크 요청, 타이머, 파일 처리 같은 작업을 Web API 영역에서 처리하고, 완료된 작업의 콜백을 이벤트 루프를 통해 메인 스레드에서 순차적으로 실행합니다. 무거운 계산이 필요하면 Web Worker처럼 별도 실행 컨텍스트를 사용해 메인 스레드의 부담을 줄일 수 있습니다.
경쟁 상태 관리(Race Condition Management)란?
여러 작업이 동시에 같은 자원이나 상태를 변경하려 할 때, 실행 순서에 따라 결과가 달라지는 문제를 제어·방지하는 것을 말한다.
브라우저 메인 스레드의 역할은?
브라우저 메인 스레드는 웹 페이지의 대부분의 작업을 처리하는 핵심 스레드입니다. CRP, JavaScript 실행, 그리고 클릭·스크롤·키보드 같은 사용자 이벤트 처리를 모두 메인 스레드에서 담당합니다.
이 모든 작업이 하나의 스레드에서 순차적으로 실행되기 때문에, JavaScript에서 무거운 연산이 오래 걸리면 렌더링이나 이벤트 처리가 블로킹되어 화면이 멈추거나 버벅이는 현상이 발생합니다.
그래서 프론트엔드 성능 최적화의 핵심은 메인 스레드를 최대한 가볍게 유지하는 것입니다. 무거운 계산은 Web Worker로 분리하고, 화면 갱신이나 낮은 우선순위 작업은 requestAnimationFrame, requestIdleCallback 등을 활용해 작은 단위로 나누어 실행하는 것이 중요합니다.
CRP란?
CRP(Critical Rendering Path)는 브라우저가 HTML, CSS, JavaScript를 받아서 화면에 픽셀로 그려내기까지의 일련의 과정을 말합니다.
먼저 HTML을 파싱하여 DOM 트리를 생성하고, CSS를 파싱하여 CSSOM 트리를 생성합니다. 이 둘을 결합하여 실제 화면에 표시될 요소들로 구성된 렌더 트리를 만들고, 각 요소의 위치와 크기를 계산하는 레이아웃(Layout) 단계를 거친 뒤, 최종적으로 화면에 픽셀을 그리는 페인트(Paint) 단계를 수행합니다.
프론트엔드 성능 최적화에서 CRP를 이해하는 것이 중요한 이유는, 이 경로를 최소화하고 빠르게 완료할수록 초기 렌더링 속도가 빨라지기 때문입니다. 예를 들어 렌더링을 차단하는 CSS는 최소화하고, JavaScript에는 async나 defer를 적용하며, 리소스 크기를 줄이는 것 등이 CRP 최적화 방법에 해당합니다.
DNS란?
DNS는 사람이 읽기 쉬운 도메인 이름을 실제 네트워크 통신에 필요한 IP 주소로 변환해 주는 시스템입니다.
예를 들어 브라우저에 `example.com`을 입력하면, 브라우저는 먼저 DNS 조회를 통해 `example.com`에 연결된 IP 주소를 찾고, 그 IP 주소의 서버로 요청을 보냅니다.
DNS는 한 서버가 모든 도메인의 IP 주소를 알고 있는 구조가 아니라, 단계적으로 물어보는 구조입니다. 먼저 루트 DNS 서버는 `.com`, `.kr` 같은 최상위 도메인을 담당하는 서버가 어디인지 알려주고, TLD DNS 서버는 `example.com` 같은 도메인을 담당하는 네임서버가 어디인지 알려줍니다. 마지막으로 권한 있는 네임서버가 `example.com`의 실제 IP 주소를 알려줍니다.
DNS 응답은 브라우저나 운영체제, DNS 서버에 일정 시간 캐시될 수 있습니다. 이 캐시 유지 시간을 TTL이라고 하며, TTL 때문에 도메인 설정을 바꿔도 전 세계에 즉시 반영되지 않고 어느 정도 전파 시간이 걸릴 수 있습니다.
렌더링을 차단하는 CSS를 최소화하는 방법은?
렌더링을 차단하는 CSS를 최소화한다는 것은 CSS를 무조건 적게 작성하라는 뜻이 아니라, 첫 화면을 그리기 전에 반드시 필요한 CSS만 우선 처리하게 만든다는 의미입니다.
브라우저는 CSSOM이 준비되어야 렌더 트리를 만들 수 있으므로, 큰 전역 CSS나 사용하지 않는 스타일이 초기 로딩에 포함되면 첫 렌더링이 늦어질 수 있습니다.
실무에서는 사용하지 않는 CSS를 제거하고, 페이지나 컴포넌트 단위로 CSS를 분리하며, 첫 화면에 필요한 핵심 스타일은 먼저 제공하고 나머지 스타일은 이후에 로드하는 방식으로 최적화합니다. 또한 외부 폰트나 CSS 라이브러리가 초기 렌더링을 막지 않도록 필요한 범위만 불러오는 것도 중요합니다.
script의 defer와 async란?
defer는 script를 HTML 파싱과 병렬로 다운로드하고, 파싱 완료 후 작성 순서대로 실행됩니다. 실행 순서가 중요한 경우에 사용합니다.
async는 script를 HTML 파싱과 병렬로 다운로드하고, 다운로드 완료 즉시 실행됩니다. 실행 순서가 중요하지 않는 경우 사용합니다.
Web Worker란?
Web Worker는 브라우저에서 메인 스레드와 별도의 백그라운드 스레드에서 JavaScript를 실행할 수 있게 해주는 API입니다. 별도의 이벤트 루프를 가집니다.
JavaScript는 기본적으로 싱글 스레드로 동작하기 때문에, 복잡한 연산이 실행되면 UI가 멈추거나 버벅이는 문제가 발생합니다. Web Worker를 사용하면 이런 무거운 작업을 별도 스레드에서 처리하므로 메인 스레드는 UI 렌더링에 집중할 수 있어 사용자 경험을 유지할 수 있습니다.
대용량 데이터 파싱, 이미지 처리, 암호화 연산 등 CPU 집약적인 작업에 활용하기 적합합니다. 하지만 DOM에 접근하지 못하고 대부분 프론트엔드 작업은 그렇게 무겁지 않기 때문에 많이 사용되지 않습니다.
requestAnimationFrame이란?
브라우저가 다음 화면을 그리기 직전에 특정 콜백 함수를 실행해 달라고 요청하는 Web API입니다.
일반적으로 setTimeout이나 setInterval을 사용해 애니메이션을 구현할 수도 있지만, 이 방식들은 브라우저의 실제 렌더링 주기와 동기화되지 않기 때문에 프레임이 누락되거나 불필요한 연산이 발생할 수 있습니다. 반면 requestAnimationFrame은 브라우저의 리페인트 타이밍에 맞춰 콜백을 실행하므로, 훨씬 부드러운 애니메이션을 구현할 수 있습니다.
또한 사용자가 다른 탭으로 이동하거나 브라우저가 백그라운드 상태가 되면 호출 빈도를 자동으로 줄이거나 중단하기 때문에, CPU와 배터리 자원을 절약할 수 있다는 장점도 있습니다.
실무에서는 JavaScript 기반의 커스텀 애니메이션뿐만 아니라, 스크롤 이벤트 핸들러, DOM 크기나 위치 변경, 숫자 카운트 등에 사용됩니다. React에서 사용할 경우에는 useEffect 내부에서 호출하고, 클린업 함수에서 cancelAnimationFrame으로 반드시 취소해 주어야 메모리 누수를 방지할 수 있습니다.
requestIdleCallback이란?
requestIdleCallback은 브라우저가 해야 할 작업을 모두 마치고 여유 시간이 생겼을 때 콜백을 실행해 달라고 요청하는 Web API입니다.
requestAnimationFrame이 "다음 화면을 그릴 때 실행해줘"라는 높은 우선순위의 요청이라면, 이것은 "지금 바쁘지 않을 때 실행해줘"라는 낮은 우선순위의 요청입니다. deadline 객체의 timeRemaining()으로 남은 여유 시간을 확인하며, 시간이 부족하면 중단하고 다음 유휴 시간에 이어서 처리하는 방식으로 구현합니다.
실무에서는 분석 로그 전송, 리소스 프리페칭, 캐시 정리처럼 당장 화면에 영향을 주지 않는 백그라운드 작업에 주로 활용됩니다. 다만 Safari에서 아직 지원하지 않아 폴리필이 필요합니다.
콜 스택이란?
콜 스택은 함수 실행 정보를 관리하는 스택 자료구조입니다. 함수가 호출되면 스택에 쌓이고, 실행이 끝나면 제거되며, 이를 통해 함수의 실행 순서를 관리합니다.
일반적으로 스레드마다 자신만의 콜 스택을 가집니다. 브라우저에서는 메인 스레드 위에서 JavaScript 엔진(V8 등)이 동작하며, JavaScript 엔진은 내부적으로 콜 스택을 관리해 함수 실행을 처리합니다. JavaScript는 하나의 콜 스택에서 함수들을 순차적으로 실행하기 때문에 싱글 스레드 방식으로 동작합니다.
실행 컨텍스트란?
실행 컨텍스트는 콜 스택에 쌓이는 각각의 항목으로, 함수나 코드가 실행되는 환경 정보를 담고 있습니다. 내부적으로 변수, this, 스코프 체인 등의 정보를 관리하는 렉시컬 환경을 가지며, 함수가 호출될 때마다 새로운 실행 컨텍스트가 생성되어 콜 스택에 push되고, 실행이 끝나면 pop됩니다.
렉시컬 환경이란?
렉시컬 환경은 실행 컨텍스트 내부에서 변수와 스코프 정보를 실제로 관리하는 구조입니다.
크게 두 가지로 구성되는데, 첫째는 환경 레코드로 현재 스코프 내의 변수, 함수 선언, this 바인딩 등 식별자 정보를 저장합니다. 둘째는 외부 렉시컬 환경 참조로 상위 스코프의 렉시컬 환경을 가리킵니다. 이 외부 참조가 체인처럼 연결된 것이 바로 스코프 체인이며, 현재 스코프에서 변수를 찾지 못하면 이 참조를 따라 상위 스코프로 올라가며 탐색하게 됩니다.
그리고 "렉시컬(Lexical)"이라는 이름에서 알 수 있듯이, 이 환경은 함수가 호출된 위치가 아니라 코드상에 작성된 위치에 의해 결정됩니다. 이 특성 덕분에 클로저가 가능한데, 함수가 자신이 선언된 시점의 렉시컬 환경을 기억하고 있기 때문에, 외부 함수의 실행이 끝나더라도 그 변수에 계속 접근할 수 있는 것입니다.
클로저란?
클로저란 함수가 자신이 선언된 시점의 렉시컬 환경을 기억하여, 해당 스코프 밖에서 실행되더라도 그 환경에 있던 변수에 계속 접근할 수 있는 현상을 말합니다.
예를 들어 외부 함수 안에서 내부 함수를 선언하고, 그 내부 함수를 반환한다고 가정하면, 외부 함수의 실행이 끝나 콜 스택에서 제거되더라도 내부 함수는 외부 함수의 변수에 여전히 접근할 수 있습니다. 이는 내부 함수가 선언 시점의 외부 렉시컬 환경에 대한 참조를 계속 유지하고 있기 때문입니다.
실무에서는 주로 데이터 은닉이나 상태 유지에 활용됩니다. 예를 들어 외부 함수 안에 count 같은 변수를 두고 내부 함수만 반환하면, 외부에서는 count에 직접 접근하지 못하지만 반환된 내부 함수는 클로저를 통해 count를 계속 읽고 수정할 수 있습니다.
useState를 클로저로 구현한다고 설명하는 경우도 있지만, React의 실제 useState가 state 값을 useState 함수 내부 변수나 컴포넌트 함수의 클로저 변수에 저장하는 방식은 아닙니다. useState가 반환하는 state는 React가 현재 컴포넌트의 Hook 저장 구조에서 꺼낸 값이며, React는 컴포넌트의 Fiber와 Hook 호출 순서, 업데이트 큐를 기준으로 state를 관리합니다.
비동기 함수란?
비동기 함수는 작업의 완료를 기다리지 않고 다음 코드를 먼저 실행할 수 있게 하는 함수입니다.
JavaScript는 싱글 스레드 언어로, 기본적으로 한 번에 하나의 작업만 처리합니다. 만약 시간이 오래 걸리는 작업을 동기적으로 처리하면, 그 작업이 끝날 때까지 브라우저가 멈춰서 사용자 경험이 나빠집니다.
비동기 함수는 이런 작업을 백그라운드에서 처리하고, 완료되면 콜백이나 Promise를 통해 결과를 받습니다. 이벤트 루프가 비동기 작업을 관리하며, 작업이 완료되면 콜백 함수를 태스크 큐에 넣어서 순차적으로 실행합니다.
이벤트 루프란?
이벤트 루프는 싱글 스레드인 JavaScript가 비동기 작업을 처리할 수 있도록 해주는 메커니즘입니다.
JavaScript 엔진은 하나의 콜 스택만 가지고 있기 때문에 한 번에 하나의 작업만 처리할 수 있습니다. 그런데 네트워크 요청이나 타이머 같은 비동기 작업이 발생하면, 이 작업은 브라우저의 Web API에 위임됩니다. Web API에서 작업이 완료되면 해당 콜백이 태스크 큐에 들어가게 되는데, 이벤트 루프는 콜 스택이 비어 있는지를 지속적으로 확인하다가, 비어 있을 때 태스크 큐에서 콜백을 꺼내 콜 스택에 올려 실행시키는 역할을 합니다.
여기서 태스크 큐는 크게 두 종류로 나뉘는데, setTimeout이나 이벤트 핸들러의 콜백이 들어가는 매크로 태스크 큐와, Promise의 콜백이 들어가는 마이크로 태스크 큐가 있습니다.
이벤트 루프는 매크로 태스크를 하나 실행한 뒤, 마이크로 태스크 큐에 있는 모든 작업을 먼저 비우고 나서야 다음 매크로 태스크를 처리합니다. 즉 마이크로 태스크가 매크로 태스크보다 우선순위가 높습니다.
이러한 구조 덕분에 JavaScript는 싱글 스레드임에도 불구하고 비동기 작업을 논블로킹으로 처리할 수 있으며, 사용자 인터랙션에 끊김 없이 반응할 수 있게 됩니다.
Web API란?
Web API는 브라우저가 제공하는 기능들의 인터페이스로, JavaScript 엔진 자체에는 포함되어 있지 않지만 JavaScript를 통해 호출할 수 있는 기능들을 말합니다.
JavaScript 엔진(V8 등)은 순수하게 JavaScript 코드를 해석하고 실행하는 역할만 담당합니다. 하지만 실제 웹 개발에서는 네트워크 요청, 타이머, DOM 조작, 위치 정보 등 브라우저 환경에서만 가능한 기능들이 필요한데, 이런 기능들을 브라우저가 Web API라는 형태로 제공하는 것입니다.
setTimeout, fetch, requestAnimationFrame, requestIdleCallback, MutationObserver, localStorage, Geolocation 등이 대표적으로 있습니다.
주의할 점은 Web API는 브라우저 환경에서만 존재하기 때문에, Node.js 같은 서버 환경에서는 동일한 API가 없거나 다른 방식으로 제공될 수 있다는 것입니다.
마이크로태스크 큐와 매크로태스크 큐의 차이는?
마이크로태스크 큐와 매크로태스크 큐의 차이는 비동기 작업의 실행 우선순위와 처리 시점의 차이를 의미합니다.
마이크로태스크 큐는 현재 실행 중인 콜 스택이 비워지자마자 즉시 처리되며, Promise의 then, catch, finally와 같은 작업들이 여기에 들어갑니다. 반면 매크로태스크 큐는 마이크로 테스크 큐가 모두 비워진 이후에 처리되며, setTimeout, setInterval, DOM 이벤트 콜백과 같은 작업들이 여기에 들어갑니다.
이러한 이유로 마이크로태스크는 매크로태스크보다 우선적으로 실행되어 비동기 처리 순서에 영향을 줍니다.
Promise란?
Promise는 JavaScript에서 비동기 작업의 완료 또는 실패를 나타내는 객체입니다. pending, fulfilled, rejected 3가지 상태가 있습니다.
Promise는 비동기 작업의 최종 결과를 약속하는 객체라고 할 수 있습니다. 작업이 아직 완료되지 않았지만, 미래에 성공하거나 실패할 것이라는 약속을 담고 있습니다.
Promise 생성과 사용은 다음과 같습니다. new Promise로 생성할 때 resolve와 reject 함수를 받고, 작업이 성공하면 resolve를 호출하고 실패하면 reject를 호출합니다. then 메서드로 성공 시 처리를 하고, catch 메서드로 실패 시 처리를 하며, finally 메서드로 성공 여부와 관계없이 실행할 코드를 작성합니다.
Promise.all이란?
Promise.all은 여러 Promise의 결과를 하나로 묶어 처리하는 메서드입니다. 모든 입력이 성공하면 완료 순서와 관계없이 입력 순서대로 결과 배열을 반환하고, 하나라도 실패하면 그 실패 이유로 빠르게 거부됩니다.
Promise.all이 비동기 작업 자체를 시작하는 것은 아닙니다. 보통 Promise는 생성하거나 비동기 함수를 호출한 시점에 작업이 시작되므로, 독립적인 작업을 함께 처리하려면 먼저 Promise들을 만든 뒤 Promise.all에 전달해야 합니다.
Promise.all이 먼저 실패하더라도 이미 시작된 다른 작업은 자동으로 취소되지 않습니다. 취소가 필요하면 AbortController처럼 작업별 취소 수단을 별도로 연결해야 합니다.
async/await란?
async/await는 JavaScript에서 비동기 처리를 동기 코드처럼 작성할 수 있게 해주는 문법이며, Promise를 기반으로 동작합니다.
async는 함수 앞에 붙여서 해당 함수가 항상 Promise를 반환하도록 만듭니다.
await는 async 함수 내부에서만 사용할 수 있으며, Promise가 처리될 때까지 함수 실행을 일시 중지합니다. Promise가 resolve되면 그 결과값을 반환하고, reject되면 에러를 throw합니다.
장점으로는 코드 가독성이 좋아지고, try-catch를 쓸 수 있습니다. 다만 await를 순차적으로 사용하면 성능이 저하될 수 있어서, 독립적인 비동기 작업들은 Promise.all을 활용해서 병렬로 처리하는 게 좋습니다.
브라우저의 작동 방식이란?
첫째, 브라우저가 URL을 파싱해서 프로토콜, 도메인, 포트, 경로를 분리합니다.
둘째, DNS 조회를 통해 도메인을 IP 주소로 변환합니다. 브라우저나 운영체제, DNS 서버에 캐시된 DNS 응답을 먼저 확인하고, 없으면 루트 DNS 서버, TLD DNS 서버, 권한 있는 네임서버 순서로 단계적으로 조회합니다.
셋째, TCP 연결을 설정합니다. 3-Way Handshake 과정을 통해 클라이언트와 서버 간 연결을 맺습니다. SYN 패킷을 보내고, 서버가 SYN-ACK로 응답하면, 클라이언트가 ACK를 보내서 연결이 완료됩니다.
넷째, HTTPS인 경우 TLS handshake를 진행합니다. 서버의 SSL 인증서를 확인하고, 암호화 방식을 협상하며, 세션 키를 전달해서 안전한 통신 채널을 만듭니다.
다섯째, HTTP 요청을 보냅니다. 서버가 요청을 처리하고 HTTP 응답을 보냅니다. 상태 코드(200, 404 등)와 함께 HTML 문서를 응답 본문에 담아 보냅니다.
3-Way Handshake / 4-Way Handshake란?
3-Way Handshake는 TCP 연결을 신뢰성 있게 수립하기 위한 초기 연결 과정으로, 클라이언트가 SYN을 보내고 서버가 SYN-ACK로 응답한 뒤 클라이언트가 ACK를 보내면서 양측이 통신 가능 상태임을 확인하는 절차입니다.
4-Way Handshake는 TCP 연결을 정상적으로 종료하기 위한 과정으로, 한쪽이 FIN을 보내 연결 종료 의사를 알리고, 상대가 ACK로 응답한 뒤 자신의 FIN을 전송하고 마지막 ACK를 받음으로써 양측이 각자의 송수신 종료를 명확히 확인하는 절차입니다.
HTTP Keep-Alive를 사용하면 요청마다 TCP 연결을 종료하지 않고 하나의 연결에서 여러 요청과 응답을 처리합니다. 이후 더 이상 연결을 사용하지 않거나 유휴 시간 제한에 도달하면 4-Way Handshake를 통해 연결을 종료합니다.
대칭키와 비대칭키란?
대칭키 암호화는 암호화와 복호화에 동일한 키인 공통키를 사용하는 방식입니다. 연산 속도가 빠르고 구현이 단순해 대용량 데이터 처리에 적합하지만, 송신자와 수신자가 사전에 같은 키를 공유해야 하므로 키 전달 과정에서 탈취될 위험이 있다는 단점이 있습니다.
비대칭키 암호화는 공개키와 개인키, 두 개의 키를 쌍으로 사용하는 방식입니다. 공개키로 암호화한 데이터는 반드시 대응하는 개인키로만 복호화할 수 있기 때문에, 공개키를 외부에 공개하더라도 안전하게 통신할 수 있습니다. 다만 대칭키 방식에 비해 연산 비용이 크고 속도가 느리다는 단점이 있습니다.
SSL/TLS에서는 이 두 방식을 함께 활용합니다. 하이브리드 암호화 방식을 채용하여 보안성과 성능을 모두 확보합니다.
하이브리드 암호화란?
하이브리드 암호화란 비대칭키와 대칭키의 장점만을 결합한 방식입니다. SSL/TLS에서 가장 일반적으로 사용되는 흐름은 다음과 같습니다.
먼저 핸드셰이크 단계에서 서버는 CA(인증 기관)가 서명한 인증서를 클라이언트에게 전달합니다. 이 인증서 안에는 서버의 공개키가 포함되어 있으며, 클라이언트는 해당 인증서를 검증하여 신뢰할 수 있는 서버인지 확인합니다.
인증이 완료되면 클라이언트는 앞으로의 통신에 사용할 공통키를 직접 생성하고, 서버의 공개키로 암호화하여 서버에 전달합니다. 서버는 자신만이 보유한 개인키로 이를 복호화하여 공통키를 안전하게 획득합니다. 공통키는 공개키로 암호화된 상태로만 전송되므로, 중간에 탈취되더라도 개인키 없이는 복호화가 불가능합니다.
이후 실제 데이터 통신은 양측이 공유한 공통키를 이용한 대칭키 방식으로 암호화하여 처리합니다. 대칭키 방식은 연산 속도가 빠르기 때문에 대용량 데이터를 주고받는 실제 통신 구간에 매우 적합합니다.
즉, "키를 나누는 과정은 비대칭키로 안전하게, 데이터를 주고받는 과정은 대칭키로 빠르게" 처리하는 것이 핵심입니다. 비대칭키만 단독으로 사용할 경우 발생하는 성능 문제와, 대칭키만 단독으로 사용할 경우 발생하는 키 전달 문제를 동시에 해결할 수 있다는 점에서 널리 사용되는 방식입니다.
TCP/UDP란?
TCP와 UDP는 전송 계층에서 데이터를 전송하는 두 가지 프로토콜로, 신뢰성과 속도에서 차이가 있습니다.
TCP는 연결 지향적이고 신뢰성 있는 프로토콜입니다. 데이터를 전송하기 전에 3-Way Handshake로 연결을 수립하고, 데이터가 순서대로 정확하게 전달되는지 확인합니다. 속도는 느리지만, 정확성이 중요한 HTTP, HTTPS 같은 서비스에 사용됩니다.
UDP는 비연결형 프로토콜로 신뢰성보다 속도를 우선합니다. 연결 수립 과정 없이 바로 데이터를 전송하며, 패킷이 순서대로 도착하는지, 손실되었는지 확인하지 않습니다. TCP보다 훨씬 빠르지만, 데이터 손실 가능성이 있습니다. 실시간성이 중요한 스트리밍, 온라인 게임 같은 서비스에 적합합니다.
HTTP Keep-Alive란?
HTTP Keep-Alive는 하나의 TCP 연결을 여러 HTTP 요청과 응답에 재사용하도록 유지하는 메커니즘입니다.
이를 통해 매 요청마다 TCP 연결을 새로 맺고 해제하는 오버헤드를 줄일 수 있어, 네트워크 지연과 서버 부하를 감소시키고 전체적인 통신 성능을 향상시킵니다.
HTTP/1.1에서는 지속 연결이 기본이므로 별도의 설정이 없어도 현재 응답 이후 TCP 연결을 유지하고 다음 요청에 재사용할 수 있습니다. 다만 `Connection: close`가 전달되거나 서버, 클라이언트, 프록시가 설정한 유휴 시간 제한에 도달하면 연결을 종료합니다.
HTTP와 HTTPS의 차이란?
HTTP와 HTTPS의 차이는 보안입니다.
HTTP(HyperText Transfer Protocol)는 클라이언트와 서버 간 데이터를 주고받는 프로토콜입니다. 데이터가 평문으로 전송되기 때문에 중간에 누군가 가로채면 내용을 그대로 볼 수 있습니다. 로그인 정보나 개인정보가 그대로 노출될 위험이 있습니다.
HTTPS(HTTP Secure)는 HTTP에 SSL/TLS 암호화를 추가한 프로토콜입니다. 데이터를 암호화해서 전송하기 때문에 중간에 가로채더라도 내용을 해독할 수 없습니다. 또한 SSL 인증서를 통해 서버의 신원을 확인할 수 있어 피싱 사이트를 방지할 수 있습니다.
SSL과 TLS란?
SSL은 클라이언트와 서버 간 데이터를 암호화하여 통신을 보호하는 보안 프로토콜입니다. TLS는 SSL의 취약점을 개선한 상위 버전으로, 현재는 SSL이 deprecated되어 실질적으로 TLS가 표준으로 사용되고 있습니다.
동작 방식은 핸드셰이크 과정을 통해 암호화 방식을 협의하고, 서버 인증서를 검증한 뒤 세션 키를 교환하여 암호화 통신을 수립하는 구조입니다. 이를 통해 암호화, 인증, 무결성 세 가지를 보장합니다.
대표적인 활용 사례로는 HTTPS가 있으며, 브라우저 주소창의 자물쇠 아이콘이 TLS로 보호된 연결임을 나타냅니다.

브라우저 렌더링 원리란? (Next.js 하이브리드 렌더링 + React 재조정)
먼저 사용자가 페이지를 요청하면, Next.js 서버는 Server Component를 실행합니다. 이 과정에서 React는 서버 환경에서 렌더 단계를 수행하며, 컴포넌트 트리를 계산하고 이를 HTML로 변환합니다. 이 결과로 프리렌더링된 HTML과 RSC Payload가 함께 생성되어 브라우저로 전달됩니다.
브라우저는 전달받은 HTML을 즉시 파싱해 DOM을 생성하고 초기 화면을 빠르게 노출합니다. 이 과정에서 브라우저는 HTML 파싱 중 발견한 CSS 리소스를 다운로드해 CSSOM을 생성하고, DOM과 CSSOM을 결합해 렌더 트리를 만든 뒤 레이아웃과 페인트, 컴포지팅 과정을 거쳐 화면을 그립니다. 이로 인해 자바스크립트가 아직 로드되지 않았더라도 사용자는 초기 화면을 볼 수 있습니다.
초기 화면이 표시된 이후, 브라우저는 Client Component에 해당하는 자바스크립트 번들을 다운로드합니다. 자바스크립트 로딩이 완료되면, React는 RSC Payload를 역직렬화하여 Server Component 부분의 트리를 복원하고, Client Component에 대해서만 렌더 단계를 수행하여 전체 Fiber 트리를 완성합니다.
이후 Client Component에 대해 커밋 단계가 진행됩니다. 일반적인 커밋 단계에서는 Fiber 트리를 기준으로 새로운 DOM 노드를 생성하여 삽입하지만, 하이드레이션에서는 이미 서버가 보낸 HTML DOM이 존재하므로 DOM을 새로 만들지 않습니다. 대신 렌더 단계에서 완성한 Fiber 트리를 기존 HTML DOM과 대조하여 각 노드를 연결하고, 이벤트 핸들러를 부착합니다. 이를 통해 정적인 HTML은 인터랙션 가능한 React UI로 전환됩니다.
이 시점부터는 state나 props가 변경되면 React는 먼저 렌더 단계에서 이전 트리와 새로운 트리를 비교해 변경 사항을 계산하고, 이 과정은 실제 DOM을 수정하지 않은 채 Virtual DOM과 Fiber 구조를 기반으로 수행됩니다. 이후 커밋 단계에서 계산된 변경 사항을 실제 DOM에 반영하고, ref 업데이트와 effect를 실행합니다.
브라우저는 DOM 변경에 따라 다시 레이아웃, 페인트, 컴포지팅 과정을 수행하며 화면을 갱신합니다. 이때 변경 내용에 따라 리플로우나 리페인트 범위가 달라지기 때문에, 불필요한 레이아웃 계산을 줄이는 것이 성능 최적화의 핵심입니다.
Rsc payload란?
RSC payload는 서버에서 실행된 React Server Component의 렌더링 결과를 HTML이 아닌 직렬화된 데이터 형태로 클라이언트에 전달하는 전송 단위이며, 클라이언트가 동일한 React 트리를 복원해 Client Component의 하이드레이션과 이후 상호작용을 가능하게 합니다.
컴포지팅 단계란?
컴포지팅 단계는 레이아웃과 페인트가 끝난 뒤, 자주 갱신되는 스타일 요소를 독립적으로 처리하기 위해 화면을 여러 레이어로 분리하고, 브라우저가 이 레이어들을 GPU에서 합성해 최종 화면을 만드는 과정입니다.
레이어 분리는 전체 화면을 다시 그리지 않고도 특정 요소만 효율적으로 갱신하기 위한 최적화 전략이며, transform이나 opacity 같은 속성 변경의 경우 리플로우나 리페인트 없이도 부드러운 화면 갱신이 가능하게 합니다.
하이드레이션이란?
하이드레이션이란 서버에서 프리렌더링된 HTML에 자바스크립트를 연결해, 정적인 마크업을 인터랙션 가능한 상태로 만드는 과정입니다.
이 과정에서 리액트는 서버에서 전달된 HTML 구조를 그대로 재사용하면서 이벤트 핸들러를 바인딩하고, 컴포넌트의 상태와 내부 로직을 복구합니다.
하이드레이션이 완료되면 이후의 상태 변경과 화면 업데이트는 클라이언트 사이드 렌더링 방식으로 처리됩니다.
하이드레이션 오류란?
하이드레이션 오류란 서버에서 생성된 HTML 구조와 클라이언트에서 실행된 React 결과가 서로 일치하지 않아 하이드레이션 과정이 실패하는 현상입니다.
하이드레이션 오류가 발생하는 이유는, React가 서버 HTML을 신뢰하고 이벤트만 연결하려면 DOM 구조가 정확히 같아야 하기 때문입니다.
구조나 텍스트가 다르면 React 내부가 가지고 있는 “현재 UI 상태”와 실제 DOM이 어긋나서, 이후 업데이트에서 잘못된 노드를 수정하거나 이벤트가 엉뚱한 요소에 붙는 등 UI가 깨질 수 있습니다.
리액트 랜더와 커밋 과정은?
리액트 렌더와 커밋 과정이란 state나 props 변경 시, 변경 사항을 계산하고 실제 DOM에 반영하는 두 단계의 렌더링 흐름을 의미합니다.
리액트는 먼저 렌더(Render) 단계에서 리액트 재조정을 수행하며, 이전 트리와 새로운 트리를 비교해 어떤 변경이 필요한지 계산합니다.
이 과정은 실제 DOM을 건드리지 않고 Virtual DOM과 파이버 트리를 기반으로 변경 계획을 수립합니다. 이때 리액트 파이버는 재조정 작업을 작은 단위로 분리하고, 우선순위를 조절하거나 작업을 중단·재개할 수 있도록 관리합니다. 이를 통해 사용자 입력과 같은 중요한 업데이트를 먼저 처리할 수 있습니다.
렌더 단계가 끝나면 커밋(Commit) 단계로 넘어가며, 계산된 변경 사항을 실제 DOM에 반영하고 ref 업데이트와 생명주기 이펙트를 실행합니다. 즉, 렌더 단계에서는 무엇이 바뀌었는지를 계산하고, 커밋 단계에서는 그 변경을 실제 화면에 적용하며, 이 전체 흐름을 효율적으로 수행하도록 만든 내부 구조가 리액트 파이버입니다.
props와 state의 차이란?
props는 부모 컴포넌트가 자식에게 전달하는 읽기 전용 입력입니다. 자식은 받은 props를 직접 수정하지 않고, 변경이 필요하면 부모가 전달한 콜백을 호출하는 방식으로 요청합니다.
state는 React가 컴포넌트의 트리 위치와 연결해 보존하는 내부 데이터입니다. setter를 호출하면 현재 함수의 값을 즉시 바꾸는 것이 아니라 다음 Render를 위한 업데이트를 예약합니다.
새 state가 이전 값과 같으면 React가 Render를 생략할 수도 있으므로 setter 호출이 항상 DOM 변경으로 이어지는 것은 아닙니다.
리액트 재조정이란?
리액트 재조정(Reconciliation)은 state나 props가 변경되었을 때, 변경 전과 후의 UI 트리를 비교하여 실제로 변경이 필요한 부분만 DOM에 반영하는 과정입니다.
리액트는 이전에 렌더링된 Virtual DOM 트리와 새로 생성된 트리를 비교해 차이를 계산하고, 그 차이만 실제 DOM에 최소한으로 적용합니다.
이 과정에서 key를 기준으로 컴포넌트를 식별해 불필요한 재생성을 방지하고, 전체를 다시 그리는 대신 성능을 최적화합니다.
Virtual DOM이란?
버츄얼 돔(Virtual DOM)은 실제 DOM의 가벼운 복사본을 메모리에 유지하면서, 변경사항을 효율적으로 반영하기 위한 프로그래밍 개념입니다.
실제 DOM을 직접 조작하는 것은 비용이 큽니다. DOM 트리를 수정하면 브라우저가 레이아웃을 다시 계산하고 화면을 다시 그리는 리플로우와 리페인트가 발생하는데, 이 과정이 성능에 큰 영향을 줍니다.
React는 이 문제를 버츄얼 돔으로 해결합니다. 상태가 변경되면 먼저 메모리상의 버츄얼 돔을 업데이트하고, 이전 버츄얼 돔과 새로운 버츄얼 돔을 비교하는 Diffing 알고리즘을 실행합니다. 그리고 실제로 변경된 부분만 찾아서 실제 DOM에 한 번에 반영하는 Reconciliation 과정을 거칩니다.
Key란?
key는 리스트 렌더링 시 각 요소를 고유하게 식별하기 위해 사용됩니다. 이를 통해 리액트가 변경된 요소를 정확히 판단할 수 있어 불필요한 재생성을 방지하고 성능을 최적화할 수 있습니다.
리액트 파이버란?
리액트 파이버는 리액트의 재조정 과정을 효율적이고 유연하게 처리하기 위해 도입된 내부 아키텍처입니다.
기존 리액트는 스택 기반의 재조정 방식을 사용했는데, 한 번 시작하면 전체 트리의 비교와 업데이트를 끝까지 동기적으로 수행해야 했습니다. 컴포넌트 수가 많아지면 메인 스레드를 오래 점유하게 되어, 사용자 입력이나 애니메이션 같은 중요한 작업이 처리되지 못해 화면이 버벅이는 문제가 있었습니다.
파이버는 이 문제를 해결하기 위해 작업의 최소 단위를 파이버 노드라는 객체로 정의하고, 재조정 작업을 작은 단위로 나누어 처리합니다.
브라우저는 보통 1초에 60번 화면을 그리기 때문에 한 프레임당 약 16.7ms의 시간이 주어지는데, 파이버는 하나의 노드를 처리한 뒤 프레임에 남은 시간을 확인하여, 시간이 부족하면 작업을 중단하고 브라우저에게 제어권을 돌려줍니다. 다음 프레임에서 여유가 생기면 중단했던 작업을 이어서 재개합니다. 이것이 가능한 이유는 기존 스택 방식과 달리 각 파이버 노드가 독립적인 객체로 작업 진행 상태를 메모리에 유지하기 때문이며, 리액트는 이를 MessageChannel 등을 활용한 자체 스케줄러로 구현하고 있습니다.
또한 파이버는 더블 버퍼링 방식을 사용하여, 현재 화면의 current 트리와 작업 중인 workInProgress 트리를 분리합니다. 렌더 단계에서 workInProgress 트리를 만들면서 변경 사항을 계산하고, 커밋 단계에서 이를 실제 DOM에 반영한 뒤 새로운 current 트리가 됩니다. 덕분에 렌더 단계에서 작업이 중단되거나 폐기되더라도 현재 화면에는 영향이 없습니다.
이러한 구조 위에서 리액트는 우선순위 기반 스케줄링을 구현합니다. 사용자의 클릭 같은 상태 변경은 높은 우선순위로, 데이터 페칭 결과에 의한 업데이트는 낮은 우선순위로 처리하여, 무거운 렌더링 중에도 사용자 인터랙션에 빠르게 반응할 수 있습니다. 이것이 리액트 18에서 정식으로 도입된 동시성 렌더링의 기반이 됩니다.
정리하면, 파이버는 재조정 작업을 작은 단위로 분리하고, 브라우저의 프레임 시간을 고려하여 작업의 중단·재개를 가능하게 하며, 우선순위에 따라 스케줄링할 수 있도록 설계된 리액트의 핵심 내부 구조입니다. 이를 통해 수백 개의 컴포넌트를 업데이트해야 하더라도 매 프레임마다 화면이 끊기지 않고 부드럽게 유지될 수 있으며, 복잡한 UI에서도 사용자 경험을 저해하지 않는 효율적인 렌더링이 가능해졌습니다.
동시성 랜더링이란?
동시성 렌더링이란 리액트 파이버 아키텍처를 기반으로, 하나의 작업에 막히지 않고 우선순위에 따라 중단·재개해 화면을 업데이트하는 렌더링 방식입니다.
리액트 파이버는 렌더링 작업을 작은 단위로 관리해 필요하면 현재 작업을 멈추고, 사용자 입력과 같은 중요한 업데이트를 먼저 처리할 수 있게 합니다.
이 구조를 통해 리액트는 UI가 멈추지 않는 부드러운 사용자 경험을 제공합니다.
스트리밍 랜더링이란?
스트리밍 렌더링이란 서버에서 생성한 HTML을 한 번에 모두 보내지 않고, 준비된 부분부터 순차적으로 브라우저에 전송해 화면을 점진적으로 보여주는 렌더링 방식입니다.
이를 통해 사용자는 전체 페이지가 완성되기 전에라도 일부 UI를 먼저 확인할 수 있어 초기 체감 속도가 개선됩니다.
스트리밍 렌더링을 하는 방법은 React의 Suspense와 서버 렌더링 환경을 사용하는 것입니다.
서버에서 렌더링 가능한 컴포넌트를 실행하고, 데이터가 아직 준비되지 않은 영역은 Suspense로 감싸 fallback UI를 먼저 내려보냅니다. 서버는 fallback이 포함된 HTML을 즉시 전송하고, 실제 데이터가 준비되는 시점에 해당 HTML 조각을 추가로 스트리밍합니다.
CSR과 SSR의 차이점이란?
CSR은 JavaScript로 페이지를 렌더링하는 방식입니다. 서버는 JavaScript 번들을 전송하고, 브라우저가 JavaScript를 다운로드하고 실행해서 DOM을 생성하고 API로 데이터를 가져와 화면을 그립니다. 초기 로딩은 느리지만 이후에는 페이지 전환이 빠르고 사용자 경험이 부드럽습니다. 하지만 SEO에 불리하고, JavaScript가 실행되기 전까지 빈 화면이 보이며, 초기 번들 크기가 크면 FCP(First Contentful Paint)가 느려집니다.
SSR은 서버에서 완성된 HTML을 생성해서 전송하는 방식입니다. 사용자가 페이지를 요청하면 서버가 데이터를 가져와서 HTML을 렌더링하고, 완성된 HTML을 브라우저에 전송합니다. 브라우저는 즉시 콘텐츠를 보여주고, 이후 JavaScript가 로드되어 상호작용이 가능해집니다(Hydration). 초기 로딩이 빠르고 SEO에 유리하며, JavaScript 없이도 콘텐츠를 볼 수 있습니다. 하지만 서버 부담이 크고, 매 페이지 요청마다 전체 페이지를 새로 받아와서 페이지 전환이 느릴 수 있습니다.
SSG / ISR / SSR이란?
SSG는 빌드 시점에 HTML을 미리 생성해 요청마다 같은 정적 결과를 빠르게 제공하는 방식입니다. 자주 바뀌지 않고 사용자별 정보가 필요하지 않은 페이지에 적합하지만, 데이터 갱신에는 재빌드나 재검증 전략이 필요합니다.
ISR은 정적 결과를 캐시해 제공하면서 시간이나 이벤트 기반 재검증으로 페이지를 갱신하는 방식입니다. 정적 응답의 속도와 데이터 최신성 사이의 균형을 맞출 수 있습니다.
SSR은 요청 시점에 서버에서 HTML을 생성하는 방식으로, 쿠키나 권한처럼 요청마다 달라지는 정보를 반영하기 좋습니다. 다만 데이터 캐시와 서버 위치, 처리량에 따라 성능이 달라지므로 SSR이 항상 가장 느리거나 항상 최신이라고 단정할 수는 없습니다.
실제 애플리케이션에서는 라우트와 데이터 요구사항에 따라 SSG, ISR, SSR을 함께 사용할 수 있습니다.
useRef란?
useRef는 Render 사이에 값을 유지하면서도, 값이 바뀌어도 새로운 Render를 요청하지 않는 Hook입니다. 타이머 ID나 이전 값처럼 화면 출력에 직접 사용하지 않는 값을 저장할 때 활용합니다.
또한 DOM 요소에 ref를 연결하면 Commit 이후 current를 통해 해당 DOM 노드에 접근할 수 있습니다. 포커스 이동이나 크기 측정처럼 명령형 DOM API가 필요한 경우에 사용합니다.
다만 ref.current의 변경은 화면을 자동으로 갱신하지 않으므로, UI에 표시되어야 하는 값은 state로 관리해야 합니다.
RESTful API란?
RESTful API는 REST 아키텍처 원칙을 따르는 API를 말합니다. REST는 자원을 URL로 표현하고 HTTP 메서드로 통해 해당 자원에 대한 행위를 정의합니다.
RESTful API의 핵심 원칙은 첫째, 클라이언트와 서버의 역할이 명확히 분리됩니다. 둘째, 무상태성으로 각 요청은 독립적이고 서버는 클라이언트의 상태를 저장하지 않습니다.
실무에서는 GET으로 조회, POST로 생성, PUT이나 PATCH로 수정, DELETE로 삭제하는 방식으로 구현하며, URL은 명사형으로 자원을 표현하고 HTTP 메서드는 동사로 표현합니다.
CORS란?
CORS는 Cross-Origin Resource Sharing의 약자로, 다른 Origin의 리소스에 접근할 수 있도록 허용하는 브라우저의 보안 메커니즘입니다.
웹 브라우저는 기본적으로 Same-Origin Policy, 즉 동일 Origin 정책을 따릅니다. Origin은 scheme(프로토콜), host, port로 구성되며, 이 중 하나라도 다르면 다른 Origin으로 판단합니다.
CORS는 서버가 특정 Origin의 요청을 허용하도록 설정할 수 있게 해줍니다. 서버가 응답 헤더에 Access-Control-Allow-Origin을 포함시키면 브라우저가 해당 Origin의 요청을 허용합니다.
preflight는 실제 요청을 보내기 전에 브라우저가 OPTIONS 요청으로 서버에 먼저 확인하는 과정입니다. 브라우저는 이 요청을 통해 실제 요청에서 사용할 HTTP 메서드와 헤더를 서버가 허용하는지 확인합니다.
다만 모든 CORS 요청에서 preflight가 발생하는 것은 아닙니다. 일부 조건을 만족하는 단순 요청은 preflight 없이 바로 서버로 전송됩니다. GET이나 HEAD 요청이고 커스텀 헤더가 없으면 보통 preflight 없이 전송되며, POST도 Content-Type이 application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나이고 커스텀 헤더가 없으면 단순 요청이 될 수 있습니다.
CORS 오류는 보통 서버의 CORS 응답 헤더가 실제 브라우저 요청 조건과 맞지 않을 때 발생합니다.
예를 들어 Access-Control-Allow-Origin에 현재 프론트엔드 Origin이 없으면 브라우저는 응답을 프론트엔드 코드에 전달하지 않습니다.
withCredentials: true 또는 credentials: "include"처럼 쿠키를 포함해 요청하는 경우에는 조건이 더 엄격합니다. 이때 서버가 Access-Control-Allow-Origin을 *로 응답하거나, Access-Control-Allow-Credentials: true를 함께 보내지 않으면 브라우저가 응답을 차단합니다.
서버의 Access-Control-Allow-Methods에 실제 요청 메서드가 없거나, 커스텀 헤더, Authorization, Content-Type 같은 요청 헤더가 Access-Control-Allow-Headers에 허용되어 있지 않으면 실패합니다.
호이스팅이란?
호이스팅은 JavaScript에서 변수나 함수 선언이 스코프의 최상단으로 끌어올려지는 것처럼 동작하는 현상입니다. 실제로 코드가 이동하는 건 아니고, JavaScript 엔진이 실행 컨텍스트를 생성할 때 선언부를 먼저 메모리에 등록하기 때문에 발생합니다.
var는 호이스팅될 때 선언과 동시에 undefined로 초기화됩니다. 그래서 선언 전에 접근해도 에러가 나지 않고 undefined를 반환합니다.
let과 const은 TDZ이라는 구간에 들어가게 되는데, 선언은 호이스팅되지만 초기화가 되지 않은 상태입니다. 그래서 실제 선언문을 만나기 전에 접근하려고 하면 ReferenceError가 발생합니다.
function 함수는 선언과 함께 함수 본문까지 모두 메모리에 등록되기 때문에, 함수 선언보다 위에서 호출해도 정상적으로 동작합니다.
반면 화살표 함수를 포함한 함수 표현식은 변수에 함수를 할당하는 방식이기 때문에, 변수의 호이스팅 규칙을 따릅니다. var로 선언하면 변수는 호이스팅되지만 undefined 상태이고, let이나 const로 선언하면 TDZ에 들어가서 ReferenceError가 발생합니다.
이벤트 버블링이란?
이벤트 버블링은 자식 요소에서 발생한 이벤트가 부모 요소로 전파되어 올라가는 현상입니다.
DOM 트리에서 특정 요소에 이벤트가 발생하면, 그 요소의 이벤트 핸들러가 실행된 후 부모 요소, 그 위의 부모 요소 순서로 계속 올라가면서 각각의 이벤트 핸들러가 실행됩니다.
이벤트 캡쳐링이란?
이벤트 캡처링은 이벤트가 최상위 부모 요소에서 시작해서 실제 이벤트가 발생한 타겟 요소까지 내려가는 전파 방식입니다.
이벤트 전파란?
이벤트 전파란, DOM에서 이벤트가 발생했을 때 해당 이벤트가 트리 구조를 따라 캡처링 단계(최상위 → 타겟), 타겟 단계, 버블링 단계(타겟 → 최상위) 순서로 전달되는 흐름을 말합니다.
이벤트 위임이란?
이벤트 위임은 여러 자식 요소에 각각 이벤트 핸들러를 등록하지 않고, 부모 요소 하나에만 이벤트를 등록해서 자식 요소들의 이벤트를 처리하는 기법입니다.
이 패턴은 이벤트 버블링 원리를 활용합니다. 자식 요소에서 이벤트가 발생하면 부모로 전파되는 특성을 이용해서, 부모에서 event.target으로 실제 이벤트가 발생한 요소를 파악하고 처리합니다.
장점은 세 가지입니다. 메모리 효율성이 높습니다. 동적으로 추가되는 요소에도 자동으로 이벤트가 적용됩니다. 코드가 간결해지고 유지보수가 쉬워집니다. React 같은 프레임워크도 내부적으로 이 패턴을 사용해서 성능을 최적화하고 있습니다.
라이브러리와 프레임워크의 차이란?
라이브러리와 프레임워크의 핵심 차이는 제어권입니다.
라이브러리는 내가 필요할 때 호출해서 사용하는 도구입니다. 내가 코드의 흐름을 제어하며, 필요한 기능만 가져다 씁니다.
프레임워크는 전체 애플리케이션의 구조를 제공하고, 내가 작성한 코드를 프레임워크가 호출합니다.
합성 이벤트란?
합성 이벤트는 React가 브라우저의 네이티브 이벤트를 감싸 React 이벤트 핸들러에 일관된 인터페이스로 전달하는 객체입니다.
preventDefault, stopPropagation 같은 공통 메서드를 같은 방식으로 사용할 수 있고, 필요한 경우 nativeEvent로 원본 이벤트에 접근할 수 있습니다. 다만 React가 모든 브라우저의 네이티브 동작 차이까지 완전히 같게 만드는 것은 아닙니다.
React 17 이후 웹 환경에서는 과거처럼 합성 이벤트 객체를 풀링해 재사용하지 않으므로 비동기 코드에서 값을 읽기 위해 persist를 호출할 필요가 없습니다.
커링이란?
커링은 여러 개의 인자를 받는 함수를 인자를 하나씩 받는 함수들의 연속으로 변환하는 함수형 프로그래밍 기법입니다.
일반적으로 함수는 모든 인자를 한 번에 받지만, 커링된 함수는 첫 번째 인자를 받으면 다음 인자를 받는 새로운 함수를 반환하고, 이 과정을 반복해서 모든 인자를 받으면 최종 결과를 반환합니다.
커링의 주요 장점은 부분 적용과 함수 재사용성입니다. 단점은 코드 가독성이 떨어질 수 있다는 것입니다.
context와 state의 차이란?
state는 컴포넌트 내부에서 관리하는 로컬 데이터이며, 해당 컴포넌트와 그 자식 컴포넌트에서만 사용할 수 있습니다. 데이터를 자식에게 전달하려면 props를 통해 내려줘야 하는데, 컴포넌트 계층이 깊어지면 props drilling 문제가 발생합니다.
context는 전역적으로 데이터를 공유하기 위한 방법입니다. createContext로 생성하고 Provider로 값을 제공하면, 트리의 어느 깊이에 있는 컴포넌트든 useContext로 바로 접근할 수 있습니다. props를 여러 단계 전달할 필요 없이 필요한 곳에서 직접 가져다 쓸 수 있어서 props drilling 문제를 해결합니다.
상태의 불변성이란?
상태의 불변성은 React에서 state를 직접 수정하지 않고 새로운 객체나 배열을 생성하여 변경하는 원칙입니다.
React는 상태가 변경되었는지 확인할 때 얕은 비교를 사용합니다. 객체의 참조값이 달라졌는지만 확인하기 때문에, 기존 state를 직접 수정하면 참조값이 같아서 React가 변경을 감지하지 못하고 리렌더링이 발생하지 않습니다.
웹 스토리지란?
웹 스토리지는 브라우저가 같은 출처 단위로 문자열 데이터를 저장하는 동기식 API이며 localStorage와 sessionStorage로 나뉩니다.
localStorage는 명시적으로 삭제하거나 브라우저 정책으로 제거되기 전까지 브라우저를 다시 열어도 유지될 수 있습니다. 같은 출처의 문서가 접근할 수 있지만 쿠키처럼 서버 요청에 자동으로 포함되지는 않습니다.
sessionStorage는 같은 출처 안에서도 탭의 페이지 세션별로 분리되며, 일반적으로 해당 탭을 닫으면 제거됩니다.
읽기와 쓰기가 메인 스레드에서 동기적으로 처리되므로 큰 데이터나 빈번한 접근에는 적합하지 않습니다. 객체는 JSON 등으로 직렬화해야 하며, 복잡하거나 큰 데이터에는 IndexedDB 같은 비동기 저장소를 고려합니다.
인증 상태를 유지하는 방식이란?
HTTP는 기본적으로 이전 요청을 기억하지 않는 stateless 프로토콜입니다. 그래서 로그인 이후의 요청에서도 사용자가 누구인지 알기 위해 별도의 인증 상태 유지 방식이 필요합니다.
대표적인 방식은 서버 세션 기반 인증과 JWT 기반 인증입니다. 서버 세션 기반 인증은 서버가 사용자 인증 상태를 저장해두고, 클라이언트는 그 상태를 찾기 위한 세션 ID를 보냅니다. JWT 기반 인증은 서버가 서명된 토큰을 발급하고, 이후 요청에서는 토큰의 signature와 만료 시간 등을 검증해 사용자를 식별합니다.
세션 기반 인증 방식이란?
세션 기반 인증은 서버가 사용자 인증 상태를 서버 저장소에 보관하는 방식입니다.
사용자가 로그인하면 서버는 세션 ID를 만들고, 세션 저장소에 이 세션 ID와 연결된 사용자 정보를 저장합니다. 이후 요청이 들어오면 서버는 클라이언트가 보낸 세션 ID로 세션 저장소를 조회해 사용자를 식별합니다.
JWT 기반 인증 방식이란?
JWT 기반 인증은 서버가 사용자 정보를 담은 토큰을 만들고, signature로 서명해 클라이언트에 전달하는 방식입니다.
JWT는 header, payload, signature로 구성됩니다. payload에는 userId, role, exp 같은 정보를 담을 수 있지만, 암호화가 아니라 인코딩된 값이므로 비밀번호 같은 민감한 정보는 담지 않아야 합니다.
요청이 들어오면 서버는 JWT를 저장소에서 찾는 대신, signature와 만료 시간을 검증해 이 토큰을 신뢰할 수 있는지 판단합니다. 보통 access token은 실제 API 요청 인증에 사용하고 만료 시간을 짧게 가져가며, Refresh Token은 access token이 만료되었을 때 새 access token을 발급받는 용도로 사용합니다. 필요한 경우 payload의 userId로 사용자 정보를 DB에서 조회할 수 있습니다.
인증 값을 서버에 보내는 방식이란?
세션 ID나 JWT 같은 인증 값은 API 요청에서 서버가 사용자를 식별할 수 있도록 함께 전달되어야 합니다. 대표적인 전달 방식은 Authorization 헤더의 Bearer 방식과 쿠키 자동 전송 방식입니다.
Bearer 방식은 클라이언트가 요청 헤더에 Authorization: Bearer {token} 형태로 인증 값을 직접 넣어 보내는 방식입니다. JWT access token을 보낼 때 자주 사용되며, 브라우저가 자동으로 붙여주는 값이 아니기 때문에 프론트엔드 코드에서 명시적으로 처리합니다.
쿠키 자동 전송 방식은 서버가 Set-Cookie로 세션 ID나 JWT를 내려주면, 브라우저가 조건에 맞는 요청에 Cookie 헤더를 자동으로 포함시키는 방식입니다. HttpOnly를 사용하면 JavaScript에서 인증 값을 직접 읽기 어렵게 만들 수 있지만, 쿠키는 자동 전송되므로 CSRF 방어를 함께 고려해야 합니다.
SEO란?
SEO는 검색 엔진 최적화로, 웹사이트가 구글이나 네이버 같은 검색 엔진에서 상위에 노출되도록 개선하는 작업입니다.
검색 엔진은 크롤러로 웹 페이지를 수집하고, 콘텐츠를 분석해서 색인을 만들고, 사용자가 검색하면 관련성과 품질을 평가해서 순위를 매깁니다. SEO는 이 과정에서 웹사이트가 잘 평가받도록 최적화하는 것입니다.
콘텐츠 최적화는 적절한 키워드를 사용하고, 시멘틱 태그를 사용하며, 이미지에 alt 속성을 추가합니다.
구조적 최적화는 sitemap.xml로 페이지 목록을 제공하고, robots.txt로 크롤링 규칙을 설정합니다. 또한 모바일 친화적인 반응형 디자인과 HTTPS 사용도 중요합니다.
웹 접근성이란?
웹 접근성은 장애가 있는 사람, 고령자, 다양한 환경의 사용자 등 모든 사람이 웹사이트를 차별 없이 이용할 수 있도록 보장하는 것입니다.
시맨틱 HTML을 사용해서 구조를 명확히 하고, 이미지에 alt 속성으로 대체 텍스트를 제공하며, 키보드 탐색이 가능하도록 포커스 순서를 관리하고, ARIA 속성으로 동적 콘텐츠의 역할과 상태를 알려줍니다.
웹 최적화란?
웹 최적화는 웹사이트를 더 빠르게 로드하고 부드럽게 동작하도록 개선하는 작업입니다.
첫째, 이미지 최적화입니다. WebP 포맷 사용, 압축, lazy loading으로 이미지 로딩 속도를 개선합니다.
둘째, 번들 크기 줄이기입니다. 코드 스플리팅과 트리 쉐이킹으로 불필요한 코드를 제거하고 필요한 것만 로드합니다.
셋째, 렌더링 최적화입니다. React.memo, useMemo, useCallback로 불필요한 리렌더링을 방지하고, 가상 스크롤로 긴 리스트를 효율적으로 처리합니다.
넷째, 캐싱과 CDN 사용입니다. 자주 사용하는 리소스를 캐싱하고 CDN으로 전 세계에서 빠르게 제공합니다.
다섯째, SSR/SSG 활용입니다. 서버에서 HTML을 미리 생성해서 초기 로딩을 빠르게 하고 SEO를 개선합니다.
여섯째, 성능 측정과 모니터링입니다. Lighthouse로 점수를 확인하고 Core Web Vitals를 추적합니다.
useCallback / useMemo란?
useCallback과 useMemo는 React에서 값이나 함수를 메모이제이션해서 불필요한 재생성을 방지하고 성능을 최적화하는 Hook입니다.
useCallback은 함수를 메모이제이션합니다. useCallback을 사용하면 의존성 배열의 값이 변경될 때만 함수를 재생성하고 그렇지 않으면 이전 함수를 재사용합니다. 주로 자식 컴포넌트에 props로 함수를 전달할 때 사용하며, 자식이 React.memo로 감싸져 있다면 함수 참조가 바뀌지 않아서 불필요한 리렌더링을 방지할 수 있습니다.
useMemo는 계산된 값을 메모이제이션합니다. 복잡한 연산의 결과를 캐싱해서 의존성이 변경될 때만 다시 계산하고, 그렇지 않으면 이전 값을 재사용합니다. 무거운 계산, 객체나 배열 생성, 필터링이나 정렬 같은 작업에 사용하며, 매 렌더링마다 같은 계산을 반복하지 않아도 됩니다.
React.memo란?
React.memo는 부모가 다시 Render될 때 이전 props와 새 props가 같다면 해당 컴포넌트의 Render를 건너뛸 수 있게 하는 성능 최적화입니다. 기본적으로 각 prop을 Object.is로 비교합니다.
memo는 성능 최적화이므로 Render 생략을 의미적 보장으로 의존하면 안 됩니다. 컴포넌트 자신의 state나 구독 중인 Context가 바뀌면 다시 Render되며, 매번 새 객체나 함수를 props로 전달하면 비교 결과도 달라집니다.
Render 비용이 작거나 props가 자주 바뀌는 컴포넌트에서는 비교 비용만 늘 수 있습니다. React DevTools Profiler 등으로 실제 병목과 재사용 효과를 확인한 뒤 적용하는 것이 좋습니다.
debounce란?
Debounce는 연속적으로 발생하는 이벤트를 그룹화해서 마지막 이벤트가 발생한 후 일정 시간이 지나면 마지막 한 번만 실행되도록 하는 기법입니다
throttle란?
Throttle은 연속적으로 발생하는 이벤트를 일정 시간 간격으로 제한해서 실행하는 기법입니다.
이벤트가 아무리 많이 발생해도 설정한 시간 간격마다 최대 한 번만 함수가 실행됩니다. 예를 들어 1초로 설정하면, 이벤트가 계속 발생하더라도 1초에 한 번씩만 함수가 호출됩니다.
html5 doctype란?
HTML5 DOCTYPE은 HTML 문서의 첫 줄에 작성하는 선언문으로, 브라우저에게 이 문서가 HTML5로 작성되었음을 알려주는 역할을 합니다.
HTML5에서는 <!DOCTYPE html>이라는 매우 간단한 형태로 작성하며, 대소문자를 구분하지 않습니다. 이전 HTML 버전들은 복잡하고 긴 DOCTYPE 선언이 필요했지만, HTML5는 이를 단순화했습니다.
클린코드란?
클린 코드는 읽기 쉽고 이해하기 쉬우며 유지보수하기 쉬운 코드를 의미합니다.
핵심 원칙은 몇 가지로 요약됩니다. 첫째, 의미 있는 이름을 사용합니다. 둘째, 함수는 한 가지 일만 합니다.  셋째, 중복을 제거합니다.
넷째, 주석보다 코드로 설명합니다. 코드 자체가 명확하면 주석이 필요 없으며, 주석이 많이 필요하다면 코드를 개선해야 한다는 신호입니다. 다섯째, 일관된 스타일을 유지합니다. 들여쓰기, 네이밍 규칙, 포맷팅을 팀 전체가 통일해서 사용합니다.
여섯째, 에러를 명확히 처리합니다.  일곱째, 테스트 가능하게 작성합니다. 
깊은 복사, 얕은 복사 차이점이란?
얕은 복사와 깊은 복사는 객체나 배열을 복사할 때 중첩된 참조 타입을 어떻게 다루는지에 따른 차이입니다.
얕은 복사는 객체의 최상위 레벨만 새로 복사하고, 내부에 중첩된 객체나 배열은 참조값만 복사합니다. 그래서 복사본의 중첩된 값을 수정하면 원본도 함께 변경됩니다. 스프레드 연산자나 Object.assign이 얕은 복사를 수행합니다.
깊은 복사는 모든 레벨의 객체를 완전히 새로 생성해서 원본과 완전히 독립적인 복사본을 만듭니다. 중첩된 객체도 모두 새로 복사되기 때문에 어느 쪽을 수정해도 다른 쪽에 영향을 주지 않습니다.
깊은 복사 방법으로는 JSON.parse(JSON.stringify())가 간단하지만 함수나 undefined를 처리하지 못하는 한계가 있습니다. Lodash의 cloneDeep이나 최신 브라우저의 structuredClone이 더 안전하고 정확합니다.
Code Splitting이란?
Code Splitting은 애플리케이션 코드를 여러 청크로 나누고 필요한 시점에 필요한 코드만 내려받도록 하는 최적화 전략입니다.
현대 빌드 도구는 진입점과 동적 import를 기준으로 청크를 구성할 수 있습니다. 라우트나 사용 빈도가 낮은 무거운 기능을 분리하면 초기 JavaScript의 다운로드·파싱·실행 비용을 줄일 수 있습니다.
React에서는 lazy와 Suspense로 컴포넌트 로딩 경계를 만들 수 있고, Next.js는 라우트 단위 분할과 dynamic import를 지원합니다.
다만 청크를 지나치게 잘게 나누면 네트워크 요청과 로딩 워터폴, 중복 의존성 비용이 늘 수 있으므로 사용자 흐름과 캐시 효율을 기준으로 분할해야 합니다.
useState의 내부 동작은?
setState를 호출하면 즉시 값이 바뀌지 않고 업데이트 큐에 추가됩니다. React는 여러 setState를 모아서 한 번에 처리하는데 이를 배치 업데이트라고 합니다. 그래서 setState를 여러 번 호출해도 리렌더링은 한 번만 발생합니다.
새로운 값과 이전 값을 Object.is로 비교해서 같으면 리렌더링을 건너뜁니다. 객체나 배열은 참조값으로 비교하기 때문에 내용이 같아도 새로운 객체를 만들면 리렌더링됩니다.
useState가 비동기인 이유는?
useState가 비동기로 동작하는 이유는 성능 최적화를 위해 여러 state 업데이트를 배치로 처리하기 때문입니다.
만약 setState가 동기로 동작한다면 setState를 호출할 때마다 즉시 리렌더링이 발생합니다. 예를 들어 하나의 함수에서 setState를 5번 호출하면 컴포넌트가 5번 리렌더링되는데, 이는 매우 비효율적이고 성능 저하를 일으킵니다.
React는 이를 해결하기 위해 setState 호출을 즉시 실행하지 않고 업데이트 큐에 쌓아둡니다. 그리고 한 번에 모든 업데이트를 처리하고 리렌더링을 한 번만 수행합니다. 이것이 배치 업데이트입니다.
비동기로 동작하기 때문에 setState 직후에 state를 읽으면 이전 값이 나옵니다. 
React 18부터는 이벤트 핸들러뿐만 아니라 setTimeout, Promise, 네이티브 이벤트 핸들러 안에서도 자동으로 배치 처리되어 더 일관되고 효율적으로 동작합니다.
함수형 프로그래밍이란?
핵심 원칙은 세 가지입니다. 첫째, 순수 함수를 사용합니다. 같은 입력에 항상 같은 출력을 반환하고, 외부 상태를 변경하지 않으며, 부수 효과가 없는 함수입니다. 둘째, 불변성을 유지합니다. 데이터를 직접 수정하지 않고 새로운 데이터를 만들어서 반환합니다. 셋째, 함수를 일급 객체로 다룹니다. 함수를 변수에 할당하고, 인자로 전달하고, 반환값으로 사용할 수 있습니다.
일급 객체란?
일급 객체는 다른 변수처럼 자유롭게 사용할 수 있는 객체를 의미합니다.
JavaScript에서 함수는 일급 객체이며, 세 가지 조건을 만족합니다. 첫째, 변수에 할당할 수 있습니다. 둘째, 함수의 인자로 전달할 수 있습니다. 셋째, 함수의 반환값으로 사용할 수 있습니다.
모듈 번들러란?
모듈 번들러는 여러 개의 JavaScript 파일과 그 의존성들을 하나 또는 여러 개의 파일로 묶어주는 도구입니다. 모듈 의존성을 분석해서 필요한 순서대로 합치고, 코드를 압축하고 최적화하며, 트랜스파일링으로 최신 문법을 구버전으로 변환한다.
대표적인 번들러는 Webpack이 가장 유명하고 강력하지만 설정이 복잡하고, Vite는 빠르고 간단해서 최근 인기가 많으며, Rollup은 라이브러리 번들링에 최적화되어 있고, Parcel은 설정 없이 바로 사용할 수 있습니다.
Webpack의 동작은 entry 파일에서 시작해서 import/require를 따라가며 의존성 그래프를 만들고, loader로 CSS나 이미지를 처리하며, plugin으로 최적화하고, 최종적으로 bundle 파일을 output에 생성합니다.
장점은 여러 파일을 하나로 합쳐서 네트워크 요청이 줄어들고, 코드 최적화와 압축으로 파일 크기가 작아지며, 최신 문법과 기능을 사용할 수 있고, 개발 환경에서 핫 리로딩으로 생산성이 높아집니다.
type, interface의 차이란?
interface의 특징은 선언 병합이 가능하다는 것입니다. 같은 이름으로 여러 번 선언하면 자동으로 합쳐집니다. 주로 객체 구조를 정의할 때 사용하고, extends로 확장합니다.
type의 특징은 더 유연하다는 것입니다. Union 타입, 튜플 등 복잡한 타입을 만들 수 있습니다. &으로 결합하며, 중복 선언은 불가능합니다.
undefined, null의 차이란?
undefined와 null은 둘 다 값이 없음을 나타내지만, 의미와 사용 목적이 다릅니다.
undefined는 변수가 선언되었지만 값이 할당되지 않았을 때 JavaScript 엔진이 자동으로 할당하는 값입니다. 함수에서 return문이 없거나 객체에 존재하지 않는 속성에 접근할 때도 undefined가 반환됩니다. 개발자가 명시적으로 할당하기보다는 시스템이 기본값으로 사용하는 것입니다.
null은 개발자가 의도적으로 값이 없음을 명시하기 위해 할당하는 값입니다. 변수에 객체가 들어갈 예정이지만 아직 없는 상태를 표현하거나, 명시적으로 비어있음을 나타낼 때 사용합니다.
useTransition과 Suspense의 차이란?
useTransition과 Suspense는 비동기 작업을 다루는 React의 도구이지만, 역할과 사용 목적이 다릅니다.
Suspense는 컴포넌트가 로딩 중일 때 fallback UI를 보여주는 선언적인 방법입니다. 비동기 리소스가 준비될 때까지 대체 콘텐츠를 렌더링하며, 주로 코드 스플리팅이나 데이터 페칭에 사용됩니다.
useTransition은 상태 업데이트의 우선순위를 낮춰서 긴급하지 않은 업데이트를 지연시키는 Hook입니다. 사용자 입력 같은 긴급한 업데이트는 즉시 반영하고, 무거운 렌더링은 백그라운드에서 처리해서 UI가 끊기지 않게 합니다.
px, em, rem의 차이란?
px은 고정된 절대 단위입니다. 1px은 화면의 한 점을 의미하며, 어디서든 같은 크기를 유지합니다.
em은 부모 요소의 폰트 크기를 기준으로 한 상대 단위입니다. 부모가 16px이면 1em은 16px이고, 2em은 32px입니다.
rem은 루트 요소(html)의 폰트 크기를 기준으로 한 상대 단위입니다. 기본값은 보통 16px이며, 중첩과 관계없이 항상 루트를 기준으로 계산되어 일관성이 있습니다.
CDN이란?
CDN은 전 세계에 분산된 서버 네트워크를 통해 콘텐츠를 빠르게 제공하는 시스템입니다.
웹사이트의 파일들은 원본 서버 한 곳에만 있으면 지리적으로 먼 사용자는 로딩이 느려집니다. CDN은 이미지, CSS, JavaScript 같은 정적 파일을 전 세계 여러 지역의 서버에 복사해두고, 사용자가 요청하면 가장 가까운 서버에서 제공해서 속도를 크게 개선합니다.
로딩 속도가 빨라져서 사용자 경험이 개선되고, 원본 서버의 부담이 줄어들며, 트래픽이 분산되어 서버 다운을 방지하고, DDoS 공격 같은 보안 위협도 완화할 수 있습니다.
대표적인 CDN 서비스는 Cloudflare, AWS CloudFront, Vercel, Netlify 등이 있으며, 많은 프레임워크와 호스팅 플랫폼이 기본으로 CDN을 제공합니다.
리액트를 사용하는 이유는?
React는 선언적인 UI 모델을 제공해 상태 변화에 따른 UI 업데이트를 예측 가능하게 만들고, 컴포넌트 단위로 책임을 분리할 수 있어 유지보수에 유리합니다. 또한 생태계가 크고 레퍼런스가 많아 실무 적용에 안정성이 있습니다.
제어 컴포넌트와 비제어 컴포넌트의 차이는?
제어 컴포넌트는 input의 value나 checked를 React state에서 전달하고, onChange를 통해 다음 값을 state에 반영하는 방식입니다. 입력값의 단일 소스가 React에 있어 검증이나 조건부 UI를 즉시 연결하기 좋습니다.
비제어 컴포넌트는 DOM이 현재 입력값을 관리하고, 필요한 시점에 ref나 폼 제출 데이터로 값을 읽는 방식입니다. 간단한 폼이나 파일 input처럼 모든 변경을 state에 저장할 필요가 없는 경우에 사용할 수 있습니다.
하나의 input을 실행 중에 제어 방식과 비제어 방식 사이에서 바꾸면 경고와 예측하기 어려운 동작이 생길 수 있으므로 처음부터 일관된 방식을 선택해야 합니다.
선언형과 명령형의 차이란?
선언형과 명령형의 차이란, 무엇을 보여줄 것인가와 어떻게 보여줄 것인가의 차이를 의미합니다.
선언형은 최종 결과만을 기술하고, 그 결과를 만드는 과정과 제어 흐름은 시스템에 위임합니다. 반면 명령형은 상태 변경과 실행 순서를 단계별로 명시해 프로그램이 어떤 절차로 동작해야 하는지를 직접 제어합니다.
SOLID 원칙이란?
객체지향 설계에서 유지보수성과 확장성을 높이기 위해 제시된 다섯 가지 핵심 설계 원칙입니다. 
단일 책임 원칙은 하나의 책임만 가지도록 하는 원칙입니다.
개방-폐쇄 원칙은 기존 코드를 직접 수정하지 않고, 새로운 기능을 추가할 수 있도록 설계하는 원칙입니다.
리스코프 치환 원칙은, 어떤 컴포넌트를 동일한 역할을 가진 다른 컴포넌트로 바꿔도
그 컴포넌트를 사용하는 쪽의 코드나 로직이 깨지지 않아야 한다는 원칙입니다.
인터페이스 분리 원칙은 하나의 큰 인터페이스를 여러 개의 작은 인터페이스로 나누어, 필요한 기능에만 의존하도록 하는 원칙입니다.
의존성 역전 원칙은 컴포넌트 안에서 구현을 직접 하지 않고, 필요한 값과 동작을 외부에서 주입받아 변경에 강한 구조를 만드는 원칙입니다.
FCP / LCP / TTI / CLS / FID / INP이란?
FCP는 페이지 로딩이 시작된 후 첫 번째 콘텐츠가 화면에 렌더링되는 시점을 측정하는 지표입니다. 사용자가 페이지에 접속했을 때 빈 화면이 아닌 실제 콘텐츠를 처음 보게 되는 시점을 의미합니다.
LCP는 뷰포트 내에서 가장 큰 콘텐츠 요소가 화면에 렌더링되는 시점을 측정합니다. 이는 사용자가 페이지의 주요 콘텐츠를 실제로 볼 수 있는 시점을 나타냅니다.
TTI페이지가 완전히 상호작용 가능한 상태가 되는 시점을 측정하는 지표입니다. 즉, 페이지가 시각적으로 렌더링되었을 뿐만 아니라 사용자의 입력에 신뢰성 있게 응답할 수 있는 시점을 의미합니다. 서버랜더링 환경에서 TTI를 줄이기 위해서는 서버컴포넌트를 적극 활용하여 JS번들 크기를 최소화해야합니다.
generateMetadata란?
Next.js 13 이상의 App Router에서 페이지나 레이아웃의 메타데이터를 동적으로 생성할 수 있게 해주는 함수입니다.
이 함수를 사용하면 각 페이지에서 title, description, Open Graph 태그, Twitter 카드 등의 메타데이터를 프로그래밍 방식으로 설정할 수 있습니다. 특히 서버 컴포넌트에서 비동기적으로 실행되기 때문에, 데이터베이스 조회나 API 호출을 통해 가져온 데이터를 기반으로 메타데이터를 생성할 수 있다는 장점이 있습니다.
Open Graph / Twitter 카드란?
Open Graph는 Facebook에서 개발한 프로토콜로, 웹 페이지가 소셜 그래프에서 어떻게 표현될지를 정의합니다. HTML의 head 태그 안에 og:title, og:description, og:image, og:url 같은 메타 태그를 추가하면, Facebook, LinkedIn, KakaoTalk, Slack 등 다양한 플랫폼에서 링크를 공유했을 때 풍부한 미리보기를 제공할 수 있습니다. 예를 들어, 블로그 글을 공유하면 제목, 설명, 썸네일 이미지가 포함된 카드 형태로 표시되어 클릭률을 높일 수 있습니다.
Twitter 카드는 Twitter(현재 X)에서 사용하는 유사한 메타데이터 시스템입니다. Twitter는 Open Graph 태그도 폴백으로 인식하지만, Twitter 카드 태그를 명시적으로 설정하면 더 나은 제어가 가능합니다. twitter:card, twitter:title, twitter:description, twitter:image를 사용합니다.
이 두 프로토콜을 적절히 구현하면 소셜 미디어에서의 가시성과 클릭률이 크게 향상되며, 브랜드 이미지를 일관되게 유지할 수 있고, 궁극적으로 트래픽 증가와 SEO 개선에도 기여합니다. 특히 마케팅이나 콘텐츠 공유가 중요한 서비스에서는 필수적으로 구현해야 하는 요소입니다.
SSO란?
SSO는 사용자가 한 번 인증하면 이후에는 같은 인증 정보를 기반으로 여러 서비스나 시스템을 다시 로그인하지 않고 접근할 수 있게 해주는 인증 방식입니다. 중앙 인증 서버에서 사용자 신원을 검증하고 토큰이나 세션을 발급해 각 서비스가 이를 신뢰하도록 구성합니다.
모노레포 / 멀티레포란?
모노레포는 여러 프로젝트를 하나의 저장소에서 관리하는 방식이고, 멀티레포는 프로젝트마다 별도의 저장소를 두는 방식입니다.
모노레포는 프로젝트 간 코드 공유와 일관된 설정 관리가 쉽고, 여러 프로젝트에 걸친 변경을 하나의 커밋으로 처리할 수 있다는 장점이 있습니다. 반면 저장소가 커지면 빌드 및 클론 시간이 늘어날 수 있습니다.
프로젝트 간 의존도가 높으면 모노레포, 독립적이라면 멀티레포가 적합하다고 생각합니다.
husky /  lint-staged란?
Husky는 Git 훅을 쉽게 설정할 수 있게 해주는 도구로, 커밋이나 푸시 같은 Git 이벤트 시점에 특정 스크립트를 자동으로 실행할 수 있게 해줍니다. 예를 들어 커밋 전에 린트나 테스트를 강제로 수행하여, 문제가 있는 코드가 저장소에 반영되는 것을 사전에 방지할 수 있습니다.
lint-staged는 Git의 스테이징 영역에 올라간 파일들에 대해서만 린트나 포맷팅 같은 작업을 실행하는 도구입니다. 전체 프로젝트가 아닌 변경된 파일만 대상으로 하기 때문에 실행 속도가 빠르고 효율적입니다.
보통 이 둘을 함께 사용하여, Husky의 pre-commit 훅에서 lint-staged를 실행하는 방식으로 구성합니다. 이를 통해 개발자가 커밋할 때 변경된 파일에 대해 자동으로 ESLint, Prettier 등을 적용하여 코드 품질과 일관성을 팀 차원에서 보장할 수 있습니다.
PNPM / NPM / YARN이란?
세 가지 모두 Node.js의 패키지 매니저로, 라이브러리 설치와 의존성 관리를 담당합니다.
NPM은 Node.js에 기본 내장되어 별도 설치 없이 사용할 수 있지만, 상대적으로 설치 속도가 느리고 디스크 사용량이 많습니다.
Yarn은 NPM의 속도와 안정성을 개선하기 위해 만들어졌으며, 병렬 설치로 속도가 빠르고 lock 파일을 통해 의존성 버전을 엄격하게 고정합니다.
PNPM은 동일한 패키지를 전역에 한 번만 저장하고 심볼릭 링크로 연결하는 방식이라 디스크 절약과 설치 속도 면에서 가장 효율적이며, 명시하지 않은 패키지에 접근하지 못하게 막아 유령 의존성 문제도 방지합니다.
브라우저 메모리 누수란?
브라우저 메모리 누수란 더 이상 사용하지 않는 메모리가 해제되지 않고 계속 점유되어 메모리 사용량이 지속적으로 증가하는 현상입니다.
JavaScript는 가비지 컬렉터가 참조되지 않는 객체를 자동으로 회수하는데, 의도치 않게 참조가 남아 있으면 회수되지 못해 누수가 발생합니다.
대표적인 원인으로는 해제하지 않은 이벤트 리스너, 정리하지 않은 setInterval/setTimeout, 클로저에 의한 불필요한 변수 참조, 제거된 DOM 요소를 변수로 계속 참조하는 분리된 DOM 노드, 그리고 전역 변수의 남용 등이 있습니다.
React에서는 useEffect의 클린업 함수에서 이벤트 리스너나 타이머를 해제하지 않는 경우가 흔한 원인입니다.
메모리 누수가 지속되면 페이지가 느려지거나 결국 브라우저 탭이 크래시될 수 있으며, Chrome DevTools의 Memory 탭에서 힙 스냅샷을 비교하여 누수를 진단할 수 있습니다.
React Hooks의 규칙은?
React Hooks에는 반드시 지켜야 하는 두 가지 규칙이 있습니다.
첫째, 최상위에서만 호출해야 합니다. 반복문, 조건문, 중첩 함수 안에서 Hook을 호출하면 안 됩니다. 이는 React가 Hook의 호출 순서에 의존하여 상태를 올바르게 관리하기 때문인데, 조건문 등으로 호출 순서가 달라지면 상태가 꼬이게 됩니다.
둘째, React 함수 컴포넌트 또는 커스텀 Hook 안에서만 호출해야 합니다. 일반 JavaScript 함수에서는 Hook을 사용할 수 없습니다.
이 규칙들을 자동으로 검사하기 위해 ESLint 플러그인인 eslint-plugin-react-hooks를 사용하면 개발 시점에 위반 사항을 미리 잡을 수 있습니다.
useEffect의 클린업 함수란?
useEffect의 클린업 함수는 Effect에서 시작한 외부 작업을 정리하기 위해 return으로 반환하는 함수입니다.
예를 들어 이벤트 리스너를 등록했으면 removeEventListener로 제거하고, setInterval을 시작했으면 clearInterval로 해제하며, 구독이나 연결을 만들었다면 구독 해제나 연결 종료를 수행합니다. 이렇게 정리하지 않으면 컴포넌트가 사라진 뒤에도 작업이 남아 메모리 누수나 중복 실행 문제가 생길 수 있습니다.
클린업 함수는 컴포넌트가 언마운트될 때 실행되고, 의존성 배열의 값이 바뀌어 Effect가 다시 실행되기 전에도 먼저 실행됩니다. 즉 기존 Effect를 정리한 뒤 새로운 Effect를 실행하는 흐름입니다.
React 컴포넌트의 실행 순서는?
React 컴포넌트의 실행 흐름은 크게 Render, Commit, Effect 실행으로 나눌 수 있습니다.
Render 단계에서는 컴포넌트 함수가 실행되고 JSX가 계산됩니다. 이때 JSX는 화면에 바로 붙는 실제 DOM이 아니라, React가 이번 화면을 어떻게 보여줘야 하는지 판단하기 위한 UI 설명값입니다.
Render가 끝나면 Commit 단계에서 React가 계산한 변경 사항을 실제 DOM에 반영합니다. 이후 ref가 연결되고, useLayoutEffect는 브라우저가 화면을 그리기 전에 동기적으로 실행됩니다. 그 다음 브라우저가 화면을 페인트하고, useEffect는 페인트 이후 비동기로 실행됩니다.
의존성이 바뀌어 Effect가 다시 실행될 때는 새 Effect가 바로 실행되는 것이 아니라, 이전 Effect의 클린업 함수가 먼저 실행됩니다. 컴포넌트가 언마운트될 때도 마지막으로 등록된 클린업 함수가 실행되어 남아 있는 외부 작업을 정리합니다.
useLayoutEffect이란?
useLayoutEffect는 useEffect와 동일한 시그니처를 가지지만, 실행 시점이 다릅니다.
useEffect는 브라우저가 화면을 페인트한 후 비동기로 실행되는 반면, useLayoutEffect는 DOM 업데이트 후 브라우저가 페인트하기 전 동기적으로 실행됩니다.
따라서 DOM의 크기나 위치를 읽어서 스타일을 조정해야 하는 경우에 useLayoutEffect를 사용하면 화면 깜빡임 없이 반영할 수 있습니다. 예를 들어 요소의 높이를 측정하여 레이아웃을 조정하거나, 스크롤 위치를 동기적으로 설정해야 할 때 적합합니다.
다만 동기적으로 실행되기 때문에 내부 로직이 무거우면 렌더링을 블로킹하여 성능에 영향을 줄 수 있으므로, 대부분의 경우에는 useEffect를 사용하고 화면 깜빡임 문제가 발생할 때만 useLayoutEffect를 사용하는 것이 권장됩니다.
고차 컴포넌트란?
고차 컴포넌트(HOC)는 컴포넌트를 인자로 받아 새로운 컴포넌트를 반환하는 함수입니다. 컴포넌트의 로직을 재사용하기 위한 패턴으로, 원본 컴포넌트를 수정하지 않고 공통 기능을 추가할 수 있습니다.
예를 들어 인증 확인, 로딩 처리, 로깅 등 여러 컴포넌트에서 반복되는 로직을 HOC로 감싸서 한 곳에서 관리할 수 있습니다. React의 React.memo나 Redux의 connect가 대표적인 HOC입니다.
다만 HOC를 과도하게 중첩하면 Wrapper Hell이 발생하고 디버깅이 어려워지는 단점이 있어, 현재는 동일한 목적을 커스텀 Hook으로 더 간결하게 달성할 수 있어 HOC의 사용 빈도가 줄어드는 추세입니다. 그럼에도 컴포넌트 자체를 감싸서 렌더링을 제어해야 하는 경우에는 여전히 유용한 패턴입니다.

Next의 캐시 전략은?
Next.js의 캐시 전략은 프로젝트에서 Cache Components를 활성화했는지에 따라 구분해서 이해해야 합니다.
Cache Components를 활성화하면 기본적으로 동적 렌더링을 사용하고, 캐시할 라우트·컴포넌트·함수에 `use cache`를 명시합니다. 캐시 수명은 `cacheLife`, 태그는 `cacheTag`, 무효화는 `updateTag`나 `revalidateTag` 같은 API로 관리할 수 있습니다.
Cache Components를 사용하지 않는 이전 모델에서는 한 번의 서버 렌더 중 중복 요청을 줄이는 Request Memoization, 요청 간 데이터를 재사용하는 Data Cache, HTML과 RSC Payload를 저장하는 Full Route Cache를 구분합니다. `fetch`에는 `cache: 'force-cache'`, `cache: 'no-store'`, `next.revalidate` 같은 옵션을 사용할 수 있습니다.
Router Cache는 두 모델 모두에서 클라이언트가 받은 라우트 세그먼트와 RSC Payload를 메모리에 보관해 이후 탐색을 빠르게 만드는 역할을 합니다.
따라서 “Next.js는 항상 네 종류의 캐시로 동작한다”라고 외우기보다, 사용 중인 Next.js 버전과 `cacheComponents` 설정을 먼저 확인한 뒤 해당 모델의 캐시 API를 설명하는 것이 정확합니다.
dynamic = "force-dynamic"이란?
Cache Components를 사용하지 않는 이전 캐시 모델에서 `dynamic = "force-dynamic"`은 라우트를 요청 시점에 렌더링하도록 강제합니다. 이 설정은 해당 라우트의 `fetch` 요청을 `cache: 'no-store'`로 처리하고 `fetchCache = 'force-no-store'`를 적용한 것과 같은 방향으로 동작하므로, 같은 라우트에서 `force-cache`로 다시 Data Cache를 사용하도록 되돌리는 설정으로 이해하면 안 됩니다.
Next.js Image의 장점은?
Next.js의 Image 컴포넌트는 이미지 크기 조정, 지연 로딩, 반응형 후보 생성과 캐싱을 지원해 일반 img 요소보다 이미지 전달을 최적화하기 쉽게 만듭니다.
width와 height 또는 fill에 필요한 컨테이너 정보를 제공하면 이미지 영역을 미리 확보해 CLS를 줄일 수 있습니다. 실제 표시 크기에 맞는 sizes 설정도 함께 작성해야 브라우저가 적절한 이미지 후보를 선택합니다.
기본 포맷과 추가 포맷은 Next.js 설정에 따라 달라집니다. WebP를 사용할 수 있지만 AVIF는 images.formats에 명시적으로 설정해야 하며, 프록시나 CDN을 사용한다면 Accept 헤더 전달도 확인해야 합니다.
화면 밖 이미지는 기본 지연 로딩의 이점을 얻을 수 있지만 LCP 이미지에는 preload 같은 우선 로딩 설정을 검토해야 합니다. 모든 이미지에 우선순위를 높이면 대역폭 경쟁으로 성능이 나빠질 수 있습니다.
Next Layout / Template이란?
Next.js에서 Layout과 Template은 모두 여러 페이지에 걸쳐 공통 UI를 제공하는 역할을 하지만, 핵심적인 차이는 상태 유지 여부입니다.
Layout은 페이지 간 이동 시 리렌더링되지 않고 상태가 유지됩니다. 예를 들어 사이드바나 네비게이션 바를 Layout에 넣으면, 사용자가 페이지를 이동해도 해당 컴포넌트가 다시 마운트되지 않고 기존 상태를 그대로 보존합니다. 불필요한 리렌더링을 방지하므로 성능상 유리하고, 대부분의 공통 UI에는 Layout을 사용합니다.
Template은 Layout과 동일한 위치에서 사용되지만, 페이지 간 이동 시 매번 새로운 인스턴스를 생성하여 상태가 초기화됩니다. 즉 이동할 때마다 컴포넌트가 언마운트되었다가 다시 마운트됩니다. 페이지 진입 시 애니메이션을 매번 실행해야 하거나, useEffect로 페이지 방문을 기록해야 하는 경우처럼 매 이동마다 초기화가 필요한 상황에서 Template을 사용합니다.
정리하면, 상태를 유지하며 공통 UI를 감싸고 싶으면 Layout, 매 이동마다 새로 초기화해야 하면 Template을 선택하면 됩니다.
CJS / ESM이란?
CJS와 ESM은 JavaScript에서 모듈을 관리하고 코드를 분리하기 위한 두 가지 모듈 시스템입니다.
CJS(CommonJS) 는 Node.js에서 사용되던 전통적인 모듈 방식으로, require와 module.exports를 사용하며 모듈을 런타임에 동기적으로 로드하는 특징이 있습니다. 이로 인해 서버 환경에는 적합하지만, 정적 분석이 어려워 트리 셰이킹 같은 최적화에는 한계가 있습니다.
반면 ESM(ES Modules) 은 JavaScript의 공식 표준 모듈 시스템으로, import와 export 문법을 사용하며 모듈 의존성을 정적으로 분석할 수 있습니다. 이 덕분에 번들러와 브라우저가 사전에 의존성을 파악해 트리 셰이킹과 같은 최적화를 수행할 수 있고, 브라우저와 Node.js 양쪽에서 공통으로 사용 가능한 현대적인 모듈 방식입니다.
트리 쉐이킹이란?
트리 쉐이킹은 번들링 과정에서 실제로 사용되지 않는 코드(dead code)를 분석해 결과물에서 제거하는 최적화 기법입니다.
주로 ESM의 정적 import/export 구조를 기반으로 동작하며, 이를 통해 번들 크기를 줄이고 초기 로딩 성능을 개선할 수 있습니다.
PWA란?
PWA는 웹 기술로 구현되지만 네이티브 앱과 유사한 사용자 경험을 제공하는 웹 애플리케이션입니다.
Service Worker를 통해 오프라인 캐싱과 백그라운드 동작을 지원하고, 웹 앱 매니페스트를 이용해 홈 화면 설치와 전체 화면 실행이 가능해지며, 이를 통해 네이티브 앱처럼 빠른 로딩과 높은 접근성을 제공하는 것이 PWA의 핵심 목적입니다.
CloudFront란?
CloudFront는 AWS에서 제공하는 CDN(Content Delivery Network) 서비스로, 전 세계 엣지 로케이션에 콘텐츠를 캐싱해 사용자에게 가장 가까운 위치에서 빠르게 전달하는 역할을 합니다.
이를 통해 정적 자산뿐 아니라 동적 요청도 지연 시간을 줄일 수 있으며, 트래픽 분산과 보안 기능을 함께 제공해 웹 애플리케이션의 성능과 안정성을 향상시킵니다.
WebSocket이란?
WebSocket은 클라이언트와 서버 간에 하나의 연결을 유지하면서 양방향으로 실시간 통신이 가능한 프로토콜입니다.
HTTP 요청-응답 방식과 달리 연결이 한 번 수립되면 서버와 클라이언트가 필요할 때마다 데이터를 주고받을 수 있어, 실시간 알림, 채팅, 실시간 데이터 스트리밍과 같은 서비스에 적합합니다.
프록시 서버와 리버스 프록시의 차이는?
프록시 서버와 리버스 프록시는 모두 클라이언트와 서버 사이에서 요청을 대신 전달한다는 공통점이 있지만, 어느 쪽을 대신하느냐와 사용 목적이 다릅니다.
프록시 서버는 클라이언트 앞단에 위치해 클라이언트를 대신하여 서버에 요청을 전달합니다. 클라이언트 입장에서는 실제 서버와 직접 통신하지 않고 프록시를 통해 접근하게 되며, 이를 통해 접근 제어, 캐싱, 보안 정책 적용, IP 은닉과 같은 기능을 수행합니다. 회사나 학교 네트워크에서 특정 사이트 접근을 제한하거나, 외부에 클라이언트 정보를 노출하지 않기 위한 용도로 자주 사용됩니다.
반면 리버스 프록시는 서버 앞단에 위치해 외부에서 들어오는 요청을 받아 내부 서버 중 하나로 전달합니다. 클라이언트는 내부 서버의 존재를 알 필요 없이 리버스 프록시만을 바라보게 되며, 이를 통해 로드 밸런싱, SSL 종료, 공통 보안 정책 적용, 내부 서버 구조 은닉이 가능합니다. 실제로는 Nginx나 CloudFront와 같은 구성에서 여러 백엔드 서버를 효율적으로 관리하기 위해 사용됩니다.
Shadow DOM이란?
Shadow DOM은 웹 컴포넌트에서 내부 구조와 스타일을 외부로부터 캡슐화하기 위한 DOM 기술입니다.
이를 통해 컴포넌트 내부의 마크업과 CSS가 전역 DOM이나 다른 컴포넌트의 스타일과 충돌하지 않도록 격리할 수 있으며, 재사용 가능하고 예측 가능한 UI 컴포넌트를 구현할 수 있습니다.
Tailwind의 장점 및 단점은?
Tailwind CSS는 유틸리티 클래스 기반으로 스타일을 구성하는 CSS 프레임워크로, 생산성과 일관성 측면에서 장단점이 명확합니다.
장점으로는 첫째, 미리 정의된 유틸리티 클래스를 조합해 빠르게 UI를 구현할 수 있어 개발 속도가 빠르고, 둘째, 디자인 토큰이 설정으로 중앙화되어 있어 팀 단위에서 스타일 일관성을 유지하기 쉽습니다. 또한 사용하지 않는 클래스가 빌드 단계에서 제거되어 결과 CSS 크기가 작다는 장점이 있습니다.
반면 단점으로는 마크업에 클래스가 과도하게 나열되어 가독성이 떨어질 수 있고, 유틸리티 기반 접근에 익숙하지 않은 경우 학습 비용이 발생합니다. 또한 추상화가 약해 복잡한 UI에서는 컴포넌트 단위의 스타일 관리 전략이 함께 필요합니다.
Zero Runtime이란?
Zero Runtime은 스타일 계산과 CSS 생성을 브라우저가 실행되는 시점이 아니라 빌드 시점에 처리하는 방식입니다.
미리 정적 CSS를 생성하기 때문에 런타임 비용을 줄일 수 있다는 장점이 있지만, 동적 스타일 표현이 제한되거나 빌드 설정이 복잡해질 수 있습니다.
CSS-in-JS의 장점 및 단점은?
CSS-in-JS는 JavaScript나 TypeScript 코드에서 스타일을 정의하고 컴포넌트와 함께 관리하는 접근 방식입니다.
라이브러리에 따라 생성된 클래스 이름으로 스타일 범위를 격리하고, props나 상태를 이용해 동적인 스타일을 표현할 수 있습니다. 스타일과 컴포넌트의 소유 관계가 가까워져 변경 범위를 파악하기 쉬운 장점도 있습니다.
반면 모든 CSS-in-JS 도구가 런타임에 스타일을 생성하는 것은 아닙니다. 런타임 방식은 스타일 생성과 주입 비용, SSR 설정 비용이 생길 수 있고, 빌드 타임 추출 방식은 동적 표현에 제약이나 별도 빌드 설정이 필요할 수 있습니다.
따라서 사용하는 도구의 실행 시점과 캐시 방식, 서버 렌더링 지원을 확인해 프로젝트 요구사항에 맞게 선택해야 합니다.
FOUC란?
FOUC는 CSS가 완전히 적용되기 전에 HTML이 먼저 렌더링되면서, 의도하지 않은 스타일이 잠깐 노출되는 현상을 의미합니다.
이는 주로 CSS 로딩이 지연되거나, 자바스크립트로 스타일을 적용하는 구조에서 발생하며, 사용자에게 화면이 깜빡이거나 깨져 보이는 인상을 주기 때문에 성능과 사용자 경험 측면에서 반드시 관리해야 하는 문제입니다.
staleTime / gcTime이란?
gcTime과 staleTime은 서버 상태 캐싱 라이브러리인 TanStack Query에서 캐시의 생명주기와 재요청 타이밍을 제어하기 위한 핵심 옵션입니다.
먼저 gcTime은 캐시 데이터가 메모리에 얼마나 오래 유지될지를 결정하는 값입니다. 구독하고 있는 컴포넌트가 모두 사라지면 해당 쿼리는 비활성 상태가 되고, 이 시점부터 gcTime 타이머가 시작됩니다. 기본값은 5분이며, 이 시간이 지나면 캐시 데이터는 완전히 삭제됩니다. 따라서 gcTime이 지난 이후에는 캐시가 존재하지 않기 때문에, 동일한 쿼리를 다시 사용할 경우 무조건 새로 요청이 발생합니다.
반면 staleTime은 캐시된 데이터가 “신선한 상태인지(stale 여부)”를 판단하는 기준 시간입니다. 기본값은 0으로, 데이터를 받아온 직후 즉시 stale 상태로 간주됩니다. 다만 stale 상태라는 것은 곧바로 재요청이 발생한다는 의미가 아니라, “재요청이 가능한 상태”가 되었음을 의미합니다.
실제 재요청은 stale 상태일 때 특정 트리거가 발생해야 실행됩니다. 예를 들어 컴포넌트가 다시 마운트될 때(refetchOnMount), 브라우저 탭에 포커스가 돌아올 때(refetchOnWindowFocus), 또는 네트워크가 재연결될 때(refetchOnReconnect)와 같은 조건에서만 재요청이 이루어집니다.
정리하면 gcTime은 캐시의 “존재 여부”를 결정하는 기준이고, staleTime은 캐시 데이터의 “신선도”를 판단하는 기준이며, 실제 네트워크 요청은 stale 상태에서 특정 이벤트 트리거가 발생했을 때 실행된다고 설명할 수 있습니다.
E2E 테스트란?
E2E(End-to-End) 테스트는 사용자의 실제 사용 흐름을 기준으로 애플리케이션의 시작부터 끝까지 전체 시스템이 정상적으로 동작하는지를 검증하는 테스트 방식입니다.
UI 조작부터 네트워크 요청, 백엔드 처리, 데이터 저장까지 포함해 여러 컴포넌트와 시스템이 연동된 상태를 실제 환경과 유사하게 테스트함으로써, 사용자가 겪을 수 있는 시나리오 단위의 오류를 확인하는 데 목적이 있습니다.
다만 실행 속도가 느리고 유지 비용이 높으며, 테스트 실패 시 원인 추적이 어렵다는 단점이 있어 핵심 사용자 흐름 위주로 제한적으로 작성하는 것이 일반적입니다.
Cypress / Playwright란?
Cypress와 Playwright는 웹 애플리케이션의 E2E 테스트를 자동화하기 위한 테스트 도구입니다.
Cypress는 브라우저 내부에서 테스트를 실행하는 구조로, 설정이 단순하고 디버깅이 직관적해 프론트엔드 개발자가 빠르게 테스트를 작성하기에 적합합니다.
반면 Playwright는 브라우저 외부에서 자동화를 제어하며, 여러 브라우저와 실제 사용자 환경에 가까운 테스트를 지원해 크로스 브라우저 테스트와 안정성이 중요한 환경에 적합합니다.
가비지 컬렉션이란?
가비지 컬렉션은 프로그램 실행 중 더 이상 참조되지 않는 메모리 객체를 자동으로 식별하고 해제하여, 개발자가 직접 메모리를 관리하지 않아도 안정적으로 메모리를 사용할 수 있도록 하는 메모리 관리 메커니즘입니다.
JavaScript에서는 가비지 컬렉션이 주로 도달 가능성(reachability) 을 기준으로 동작하며, 전역 객체나 현재 실행 중인 함수의 렉시컬 환경에서 참조할 수 없는 객체는 사용되지 않는 것으로 판단되어 수거 대상이 됩니다.
이를 통해 메모리 누수를 줄이고 애플리케이션의 안정성을 높일 수 있지만, 가비지 컬렉션 과정 자체는 런타임 비용이 발생할 수 있으므로 불필요한 참조를 남기지 않는 코드 작성이 중요합니다.
관심사 분리란?
관심사 분리는 각 코드나 모듈이 하나의 책임과 역할에만 집중하도록 분리하는 소프트웨어 설계 원칙입니다.
이를 통해 변경 사항의 영향 범위를 최소화하고, 코드의 가독성과 유지보수성을 높이며, 테스트와 확장이 쉬운 구조를 만드는 것이 목적입니다.
업스트림 / 다운스트림이란?
업스트림과 다운스트림은 시스템이나 데이터 흐름에서 기준이 되는 지점을 중심으로 앞단과 뒷단의 관계를 설명하는 개념입니다.
업스트림은 현재 컴포넌트나 서비스에 데이터나 요청을 제공하는 상위 단계를 의미하며, 의존성이나 입력의 출처가 되는 쪽입니다.
반대로 다운스트림은 현재 지점에서 발생한 결과를 전달받아 처리하는 하위 단계를 의미하며, 출력이나 영향이 전파되는 대상입니다.
이 개념을 통해 시스템 장애 전파, 의존성 관리, 데이터 흐름을 명확하게 분석할 수 있습니다.
싱글톤 패턴이란?
싱글톤 패턴은 애플리케이션 전역에서 특정 객체의 인스턴스를 하나만 생성하고 이를 공유하도록 보장하는 디자인 패턴입니다.
주로 공통 리소스를 관리할 때 사용되며, 전역 접근이 가능하다는 장점이 있지만 과도하게 사용하면 결합도가 높아지고 테스트가 어려워질 수 있어 신중한 적용이 필요합니다.
마이크로 프론트엔드란?
마이크로 프론트엔드는 하나의 프론트엔드 애플리케이션을 여러 독립적인 단위로 분리해, 각각을 개별적으로 개발·배포·운영할 수 있도록 하는 아키텍처 방식입니다.
이를 통해 팀 단위의 자율성과 배포 독립성을 높일 수 있지만, 공통 설계와 통합 전략이 부족하면 복잡도가 급격히 증가하기 때문에 명확한 경계와 규칙이 필수적입니다.
Cold Start란?
Cold Start는 서버리스 환경이나 애플리케이션에서 요청을 처리할 인스턴스가 미리 떠 있지 않은 상태에서, 최초 요청 시 실행 환경을 새로 초기화하면서 지연이 발생하는 현상을 의미합니다.
이는 함수 코드 로딩, 런타임 초기화, 의존성 설정 과정이 포함되기 때문에 응답 시간이 길어질 수 있으며, 특히 서버리스 아키텍처에서 성능 최적화 시 중요한 고려 요소입니다.
Redis란?
Redis는 메모리 기반의 키-값 구조 데이터 저장소로, 매우 빠른 읽기·쓰기 성능을 제공하는 인메모리 데이터베이스입니다.
주로 캐시, 세션 저장소, 메시지 브로커, 실시간 랭킹과 같은 용도로 사용되며, 디스크 기반 저장소에 비해 지연 시간이 매우 짧다는 장점이 있지만, 메모리를 사용하기 때문에 데이터 영속성 전략을 함께 고려해야 합니다.
로드 밸런싱이란?
로드 밸런싱은 여러 서버에 트래픽을 분산시켜 특정 서버에 부하가 집중되는 것을 방지하고, 시스템의 가용성과 확장성을 높이는 기법입니다.
이를 통해 하나의 서버 장애가 전체 서비스 장애로 이어지는 것을 막을 수 있으며, 안정적인 성능과 무중단 서비스를 제공하는 것이 목적입니다.
Git Rebase란?
Git Rebase는 한 브랜치에서 작업한 커밋들을 다른 브랜치의 최신 커밋 위로 다시 쌓아 올려, 브랜치의 기준점을 변경하고 커밋 히스토리를 직선적으로 정리하는 Git 기능입니다.
이를 통해 불필요한 merge 커밋 없이 깔끔한 커밋 로그를 유지할 수 있지만, 기존 커밋이 새로운 커밋으로 재작성되면서 해시가 변경되기 때문에 이미 공유된 브랜치에서 사용하면 히스토리 충돌이나 이력 꼬임을 유발할 수 있어 주의가 필요합니다.
Git Cherry-pick이란?
Git Cherry-pick은 다른 브랜치에 포함된 커밋 중 특정 커밋 하나를 선택해 현재 브랜치에 그대로 적용하는 Git 기능입니다.
전체 브랜치를 병합하지 않고도 필요한 변경 사항만 선별적으로 가져올 수 있어 핫픽스나 부분 기능 이식에 유용하지만, 동일한 커밋이 여러 브랜치에 중복 생성되거나 충돌이 발생할 수 있으므로 적용 목적을 명확히 하고 사용해야 합니다.
Git Fork / Clone이란?
Git Fork와 Clone은 원격 저장소를 기반으로 작업 공간을 만드는 방식이지만, 목적과 사용 맥락이 다릅니다.
Fork는 다른 사용자의 원격 저장소를 자신의 계정으로 복사해 새로운 원격 저장소를 만드는 것으로, 원본 저장소에 직접 쓰기 권한이 없을 때 독립적으로 개발한 뒤 Pull Request를 통해 기여하기 위한 협업 방식입니다. 이 방식은 원본 저장소의 안정성을 유지하면서 외부 기여를 가능하게 합니다.
반면 Clone은 기존 원격 저장소를 로컬 환경으로 그대로 복제하는 것으로, 저장소의 코드를 로컬에서 실행·수정·테스트하기 위한 가장 기본적인 작업 방식입니다. 일반적으로 동일 조직이나 권한이 있는 저장소에서 개발할 때 사용되며, 권한이 있을 경우 직접 원격 저장소에 반영할 수 있습니다.
Git Hooks / GitHub Actions이란?
Git Hooks는 커밋, 푸시 등 Git 이벤트 발생 시 로컬에서 자동으로 스크립트를 실행하는 기능입니다. 예를 들어 pre-commit 훅으로 커밋 전에 린트를 돌려 문제 있는 코드가 커밋되는 것을 방지할 수 있습니다. 로컬 환경에서 동작하므로 빠른 피드백이 가능하지만, 개발자가 우회할 수 있다는 한계가 있습니다.
GitHub Actions는 GitHub 저장소에서 push, PR 생성 등의 이벤트 시 서버(CI/CD) 환경에서 워크플로우를 자동 실행하는 기능입니다. 테스트, 빌드, 배포 등을 자동화할 수 있으며, 서버에서 실행되기 때문에 개발자가 우회할 수 없어 코드 품질을 강제할 수 있습니다.
정리하면 Git Hooks는 로컬에서 빠른 사전 검증, GitHub Actions는 서버에서 확실한 품질 보장을 담당하며, 실무에서는 둘을 함께 사용하여 로컬에서 1차로 걸러내고 CI에서 최종 검증하는 방식으로 활용합니다.
any / unknown이란?
any와 unknown은 TypeScript에서 타입 검사를 느슨하게 처리하기 위한 타입이지만, 타입 안정성 측면에서는 역할이 완전히 다릅니다.
any 는 해당 값에 대해 타입 검사를 사실상 비활성화하는 타입으로, 어떤 타입의 값이든 할당할 수 있고 어떤 연산도 제한 없이 수행할 수 있습니다. 이로 인해 컴파일 단계에서 오류를 잡을 수 없고, 런타임 오류로 이어질 가능성이 높아 타입 안정성을 해칩니다.
반면 unknown 은 값의 타입을 알 수 없음을 명시하는 타입으로, 모든 타입의 값을 할당받을 수는 있지만, 타입을 좁히기 전까지는 직접 사용할 수 없습니다. 즉, 조건문이나 타입 가드 등을 통해 타입을 명확히 한 이후에만 안전하게 사용할 수 있어, any보다 훨씬 안전한 대안입니다.
따라서 any는 불가피한 경우에만 제한적으로 사용해야 하며, 타입 안정성을 유지하려면 기본적으로 unknown을 사용하는 것이 바람직합니다.
유니온 타입 / 인터섹션 타입이란?
유니온 타입과 인터섹션 타입은 TypeScript에서 여러 타입을 조합해 표현하기 위한 타입 시스템입니다.
유니온 타입(Union Type) 은 값이 여러 타입 중 하나일 수 있음을 의미하며, A | B 형태로 표현합니다. 이 경우 공통으로 보장된 속성만 바로 사용할 수 있고, 타입 가드를 통해 실제 타입을 좁혀서 사용하는 방식이 일반적입니다.
반면 인터섹션 타입(Intersection Type) 은 여러 타입을 모두 만족하는 타입을 의미하며, A & B 형태로 표현합니다. 즉, 두 타입의 속성을 모두 가진 하나의 타입을 만들 때 사용되며, 주로 여러 역할이나 책임을 동시에 가지는 객체를 표현할 때 활용됩니다.
Pick / Omit / Partial / Readonly란?
Pick, Omit, Partial, Readonly는 TypeScript에서 기존 타입을 재사용해 새로운 타입을 만드는 유틸리티 타입입니다.
Pick은 기존 타입에서 특정 속성만 선택해 새로운 타입을 만들 때 사용하며, 필요한 필드만 명확히 드러내고 싶을 때 유용합니다.
Omit은 기존 타입에서 특정 속성을 제외한 나머지로 타입을 구성할 때 사용하며, 불필요하거나 외부에 노출되면 안 되는 필드를 제거할 때 활용됩니다.
Partial은 기존 타입의 모든 속성을 선택적으로(optional) 바꿔, 일부 값만 있어도 되는 객체를 표현할 때 사용됩니다.
Readonly는 기존 타입의 모든 속성을 읽기 전용으로 만들어, 객체가 생성된 이후 값이 변경되지 않도록 타입 수준에서 제약을 거는 데 사용됩니다.
enum / as const란?
enum과 as const는 TypeScript에서 값의 범위를 제한하고 타입을 명확히 표현하기 위한 방법이지만, 접근 방식과 특성이 다릅니다.
enum 은 관련 있는 상수 집합을 하나의 타입으로 묶는 문법으로, 숫자형 또는 문자열 기반 열거형을 정의할 수 있습니다. 런타임에 실제 객체가 생성되기 때문에 사용은 편리하지만, 번들 크기 증가와 예기치 않은 값 확장 같은 단점이 있어 최근에는 사용을 신중히 고려하는 추세입니다.
반면 as const 는 객체나 배열 리터럴을 가장 좁은 리터럴 타입과 readonly 속성으로 고정시키는 타입 단언입니다. 이를 통해 별도의 enum 선언 없이도 상수 값 집합을 안전하게 타입으로 활용할 수 있으며, 추가적인 런타임 코드가 생성되지 않아 가볍고 예측 가능한 방식입니다.
따라서 단순한 상수 집합이나 프론트엔드 코드에서는 as const 기반 패턴이 선호되고, 명확한 도메인 개념이 필요하거나 언어 차원의 열거형이 필요한 경우에만 enum을 사용하는 것이 적절합니다.
인덱스 시그니처란?
인덱스 시그니처는 TypeScript에서 객체의 키 이름을 미리 알 수 없지만, 키와 값의 타입 규칙은 명확할 때 사용하는 타입 정의 방식입니다.
이를 통해 객체가 어떤 문자열이나 숫자 키를 가지더라도, 해당 키에 대응하는 값의 타입을 일정하게 제한할 수 있으며, 동적으로 생성되는 객체나 맵 형태의 데이터를 타입 안전하게 표현할 수 있습니다.
declare 키워드와 .d.ts 파일의 용도는?
declare 키워드와 .d.ts 파일은 TypeScript에 실제 구현은 없지만 타입 정보만 존재함을 알려주기 위한 선언 수단입니다.
declare는 전역 변수, 외부 라이브러리, 또는 런타임에 이미 존재하는 값에 대해 TypeScript가 타입을 인식할 수 있도록 선언할 때 사용되며, 해당 선언은 컴파일 결과에 포함되지 않습니다.
.d.ts 파일은 이러한 선언들을 모아 관리하는 타입 선언 파일로, JavaScript로 작성된 라이브러리나 외부 환경에 대해 타입 정보를 제공함으로써 TypeScript 프로젝트에서도 타입 안전성을 유지할 수 있도록 하는 역할을 합니다.
Error Boundary란?
Error Boundary는 하위 React 컴포넌트의 렌더링 과정에서 발생한 오류를 잡아, 전체 화면이 사라지는 대신 대체 UI를 보여주는 컴포넌트입니다.
오류가 발생한 영역을 다른 화면과 격리하고 로깅할 수 있다는 장점이 있습니다. 다만 이벤트 핸들러나 비동기 콜백, 서버 사이드 렌더링에서 발생한 모든 오류를 자동으로 처리하는 것은 아니므로 오류가 발생하는 위치에 맞는 별도 처리가 필요합니다.
HTTP/2와 HTTP/3의 차이는?
HTTP/2는 하나의 TCP 연결 안에서 여러 요청과 응답을 스트림으로 다중화해 HTTP/1.1의 연결 사용 비효율을 줄입니다. 하지만 TCP 계층에서 패킷 손실이 발생하면 같은 연결의 스트림들이 함께 지연될 수 있습니다.
HTTP/3는 TCP 대신 UDP 기반의 QUIC을 사용합니다. 스트림별로 손실을 처리해 다른 스트림의 지연을 줄일 수 있고, 연결 설정과 암호화 과정을 통합해 재연결과 네트워크 전환에도 유리합니다.
Testing Library란?
Testing Library는 컴포넌트의 내부 구현보다 사용자가 화면을 찾고 조작하는 방식에 가깝게 테스트하도록 돕는 도구입니다.
역할과 접근 가능한 이름을 기준으로 요소를 찾고 실제 사용자 이벤트처럼 상호작용을 검증하기 때문에, 내부 함수나 state 구조가 바뀌어도 사용자 동작이 같다면 테스트를 유지하기 쉽습니다. 구현 세부사항보다 화면에 보이는 결과와 접근성을 중심으로 테스트하는 것이 핵심입니다.
